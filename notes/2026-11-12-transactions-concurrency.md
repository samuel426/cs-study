# 트랜잭션과 동시성

- 날짜: 2026-11-12 (Asia/Seoul)
- 정리 재개일: 2026-11-13. 중단된 기록 검증·저장 작업과 마지막 피드백 전달을 마무리한 날짜이며 별도 수업으로 세지 않는다.
- 수업: CS-03 / 데이터베이스
- 진행: 확인 문제 5/5개 답변·피드백 완료. 숙련 완료를 의미하지 않는다.
- 같은 날 [인덱스와 조회 성능](2026-11-12-indexes-query-performance.md) 5문제 이후 사용자 요청에 따라 진행한 별도 수업이다.
- 목표: 여러 변경을 하나로 묶는 이유, 업무 규칙과 원자성의 차이, 동시 갱신과 잠금, 장애 후 복구를 설명하기.
- 예제는 실제 금융 서비스의 구현·측정 사례가 아닌 일반적인 DB 학습 사례다.

## 핵심 개념

| 개념 | 설명과 적용 범위 |
|---|---|
| 트랜잭션 | 하나의 작업 단위로 다루는 DB 작업들의 묶음 |
| COMMIT | 트랜잭션의 변경을 확정 |
| 전체 ROLLBACK | 아직 커밋하지 않은 트랜잭션의 변경을 취소 |
| 원자성 · Atomicity | 작업 일부만 확정하지 않고 전체 반영 또는 전체 취소. 모든 SQL을 물리적으로 동시에 실행한다는 뜻은 아님 |
| 일관성 · Consistency | 정해진 데이터 규칙을 유지. DB가 업무 규칙을 추측하지 않으므로 검증 로직·제약 조건 등의 구현이 필요 |
| 격리성 · Isolation | 동시 실행의 간섭을 제어. 구체적인 보호 범위는 격리 수준과 읽기·쓰기 방식에 따라 달라짐 |
| 지속성 · Durability | 성공적으로 커밋된 변경을 장애 후에도 유지. 예제는 커밋 기록이 영구 저장되고 저장 장치 손상 없이 정상 복구하는 조건 |

ACID는 위 네 성질의 앞 글자다. 원자성만으로 잘못된 업무 로직이나 모든 동시성 문제가 해결되지는 않는다. 애플리케이션의 모든 오류가 언제나 자동으로 전체 롤백되는 것으로 일반화하지 않는다.

## 확인 문제와 피드백

### 1. 송금 중 실패와 전체 롤백

**질문:** 같은 트랜잭션을 지원하는 DB에서 A는 10만 원, B는 5만 원이다. A에서 B로 3만 원을 보내며 차감·입금을 하나의 트랜잭션으로 묶었다. 차감 후 입금 단계가 실패했고 커밋 전 전체 롤백을 완료했다. 수수료와 다른 거래는 없다. 이후 잔액과 A 차감만 확정하면 안 되는 이유는?

**사용자 답변:** A는 10만 원, B는 5만 원. A만 차감되면 3만 원이 공중분해되므로 거래가 전부 성공하거나 전부 실패해야 한다.

**피드백:** 잔액과 부분 확정이 송금의 의미를 깨뜨리는 이유 모두 정확하다. 진행 중 상태도 있으며, 두 가지라는 표현은 최종 변경 반영 결과를 뜻한다고 보완했다.

### 2. 모두 커밋됐으면 업무 규칙도 지켜졌을까?

**질문:** 업무 규칙은 '잔액은 음수가 될 수 없다'이다. A 2만 원, B 5만 원에서 3만 원을 송금한다. 잔액 검사와 해당 DB 제약을 구현하지 않아 차감·입금이 한 트랜잭션에서 모두 성공하고 커밋됐다. 수수료와 다른 거래는 없다. 최종 잔액과 정상 여부, 원자성만으로 충분하지 않은 이유는?

**사용자 답변 요지:** 업무 규칙 때문에 A는 2만 원 또는 0원, B는 8만 원 또는 7만 원일 것 같다. 돈이 부족한데 거래가 성공했으므로 정상은 아니다.

**피드백:** 정상으로 보지 않는 판단은 맞다. 그러나 검사 로직·제약이 없다는 조건에서 규칙이 자동으로 잔액이나 송금액을 조정한다고 생각했다. 음수를 저장할 수 있는 숫자 열에서 두 변경이 성공했다는 예제이므로 A는 -1만 원, B는 8만 원이다. 자동으로 0원에 맞추거나 2만 원만 보내지 않는다.

두 변경이 함께 확정되었으므로 원자성은 지켜졌지만 의도한 잔액 규칙은 깨졌다. 정상적인 거절·전체 롤백을 구현하면 A 2만 원, B 5만 원을 유지해야 한다. 이 설명 후 재답변은 받지 않았으므로 원자성과 일관성 구분의 숙련은 미검증이다.

### 3. 같은 재고를 읽은 두 구매

**질문:** 재고는 10개이고 T1·T2가 각각 한 개를 구매한다. 별도 트랜잭션에서 일반 SELECT로 둘 다 10을 읽고 애플리케이션에서 각자 9를 계산했다. T1이 먼저 9를 저장·커밋하고 T2도 미리 계산한 9를 저장·커밋한다. 이 순서가 허용되며 재조회·재시도·다른 거래는 없다. 실제 최종 재고, 기대 재고, 차이의 이유는?

```sql
-- 각 트랜잭션이 과거 조회 값으로 계산한 상수 9를 저장한다.
UPDATE products SET stock = 9 WHERE id = 1;
```

이는 DB에 stock = stock - 1을 요청하는 예제와 구분한다.

**사용자 답변:** 실제 재고는 9, 올바른 결과는 8이다. T1의 읽기·계산 중 T2도 진행됐기 때문이며 T1의 쓰기까지 마치고 T2가 읽도록 해야 한다.

**피드백:** 실제·기대 값과 읽기부터 쓰기까지 보호하는 방향이 정확하다. 직접적인 원인은 두 작업이 같은 과거 값에서 계산해 후속 저장이 앞선 감소 효과를 덮은 것이다. 이를 갱신 유실(lost update)이라고 설명했다. DB에서는 UPDATE 실행과 COMMIT이 다르며 다음 잠금 사례에서는 커밋까지 보호해야 한다고 보완했다. 운영체제의 읽기-계산-쓰기 동기화 사례와 연결한 복습이다.

### 4. 잠금 읽기와 커밋 시점

**질문:** MySQL InnoDB에서 T1·T2는 각각 명시적 트랜잭션을 시작하고 기본 키가 1인 같은 상품을 FOR UPDATE로 읽어 한 개씩 구매한다. T1은 10을 읽고 9로 UPDATE했지만 아직 미커밋이다. T2가 같은 행에 SELECT ... FOR UPDATE를 요청했다. 이후 T1은 정상 커밋하며 타임아웃·취소·추가 거래는 없다. T2의 즉시 읽기 가능 여부, 진행 시점과 읽는 값, T2 커밋 후 최종 재고는?

```sql
START TRANSACTION;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
-- 재고 확인과 변경 후 COMMIT 또는 전체 ROLLBACK
```

**사용자 답변:** 아직 커밋되지 않았으므로 못 읽는다. 커밋 후 9를 읽고 최종 재고는 8이다.

**피드백:** 모두 정확하다. 직접적인 대기 원인은 T1이 가진 잠금과 T2의 잠금 요청이 충돌하기 때문이다. T1 커밋 후 T2가 잠금을 얻어 9를 읽고 8로 변경·커밋한다. 해당 잠금은 커밋 또는 전체 롤백 시 해제된다. 미커밋 변경이 있으면 모든 일반 SELECT가 대기한다거나 전체 DB를 잠근다는 뜻은 아니다. 특정 사례의 흐름을 확인했으며 실제 코드 적용 능력까지 검증한 것은 아니다.

### 5. 장애 후 유지할 변경과 취소할 변경

**질문:** 초기 재고 10에서 T1·T2가 정상 커밋되어 8이 확정됐다. 이후 T3가 재고를 7로 UPDATE했지만 커밋 전에 DB 서버가 중단됐다. 커밋 기록은 영구 저장됐고 저장 장치 손상·다른 거래 없이 정상 복구한다. 복구 후 재고는 7·8·10 중 무엇이며 유지·취소할 변경과 이유는?

**사용자 답변 요지:** 8이다. 커밋되어 확정된 T1·T2는 유지하고 커밋하지 못한 T3는 취소해야 한다. 데이터 정합성이 중요하고 미커밋 작업은 정합성을 놓칠 가능성이 있기 때문이다.

**피드백:** 재고와 유지·취소 대상은 정확하다. 이유는 정합성 문제가 생길 가능성보다 커밋 여부에 따른 확정과 취소로 설명해야 한다. T1·T2의 확정된 효과를 보존하는 것은 지속성이고, 커밋되지 못한 T3의 변경 효과를 남기지 않는 것은 원자성과 연결된다.

T3의 계산이 업무 규칙에 맞더라도 커밋 전에 실패하면 확정된 결과로 남기지 않는다. 반대로 커밋됐다는 사실만으로 업무 규칙을 자동으로 만족하는 것은 문제 2에서 보았듯 아니다. 이 두 보완 문장을 사용자가 다시 설명한 것으로 기록하지 않는다.

**답변 예시:** '재고는 8개입니다. T1·T2는 커밋되었으므로 지속성에 따라 효과가 보존되어야 합니다. T3는 커밋 전에 실패했으므로 변경을 취소해야 합니다. 이는 완료되지 않은 트랜잭션의 효과를 남기지 않는 원자성과 관련됩니다.'

## 확인된 내용과 다음 복습

- 확인: 송금 전체 롤백, 갱신 유실의 실제·기대 값 및 보호 방향, FOR UPDATE 사례의 대기·커밋 후 최신 값·최종 재고, 장애 복구에서 커밋 여부에 따른 유지·취소 대상.
- 보완: 업무 규칙은 구현해야 하며 DB가 자동으로 잔액을 조정하지 않는다. UPDATE 완료와 COMMIT은 다르다. 대기의 직접 원인은 충돌하는 잠금이다. 커밋 여부와 업무 규칙의 올바름은 별개다.
- 미검증: 보완 개념의 새 사례 적용, 격리 수준별 차이, 실제 잠금 코드 작성과 복구 구현. 격리 수준 전체를 학습 완료했다고 기록하지 않는다.
- 2026-11-12에는 인덱스 5문제와 트랜잭션 5문제, 총 10문제 답변·피드백을 마쳤다. 추가 질문 없이 종료한다.
- 다음 기본 주제: Redis 요청 제한. 첫 복습을 포함해 총 5문제로 진행하고, 오늘의 원자성·일관성 구분과 동시 실행의 보호 범위를 연결한다.
