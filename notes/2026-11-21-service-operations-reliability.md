# 서비스 운영과 장애 대응: 세션 공유, 데이터 보존, 타임아웃과 재시도

- 학습 기간: 2026-11-20~2026-11-21 (Asia/Seoul)
- 수업: CS-11 / 서비스 운영 · 세션과 트랜잭션 복습
- 진행: 20일 문제 1을 제시한 뒤 중단했고, 21일 문제 1~5에 답해 5/5문제 답변·피드백을 마쳤다. 숙련 완료를 뜻하지 않는다.
- 목표: 요청 경로와 저장 위치, 서버 처리 결과와 응답 수신을 구분하고 재시도의 위험과 대응을 설명하기.
- 사용자 요청에 따라 이 수업 정리 후 같은 날 CS-12 종합 설명 연습 5문제로 이어간다. CS-12의 미응답 문제를 완료로 세지 않는다.

## 핵심 개념

| 개념 | 역할과 한계 |
|---|---|
| 리버스 프록시 | 서버 앞에서 요청을 받아 뒤쪽 서버에 전달하고 응답을 돌려주는 중계 역할 |
| 로드 밸런싱 | 요청을 여러 서버에 분산. 서버들의 메모리까지 자동 공유하는 기능은 아님 |
| 공유 세션 저장소 | 여러 애플리케이션이 같은 세션 기록을 조회하도록 구성. 연결 설정·접근 비용·가용성 고려 필요 |
| 이미지와 컨테이너 | 이미지는 프로그램·실행 환경을 담은 원본, 컨테이너는 이를 바탕으로 만든 격리된 실행 환경 |
| 컨테이너 전용 쓰기 공간 | 실행 중 생긴 파일이 원본 이미지에 자동 반영되지 않으며 컨테이너 삭제 시 함께 사라짐 |
| 볼륨 | 컨테이너와 독립적으로 유지할 수 있는 저장 공간. 볼륨 자체의 삭제·호스트 장애에 대한 보호까지 자동 보장하는 것은 아님 |
| 타임아웃 | 호출자가 제한 시간 내 응답을 받지 못함. 서버 작업의 취소·롤백을 보장하지 않음 |
| 멱등성 | 같은 요청을 반복해도 의도한 서버 상태 변화가 한 번 적용한 것과 같도록 하는 성질 |
| 멱등성 키 | 같은 업무 요청의 재시도를 식별. 서버의 결과 보관·중복 방지 구현이 필요 |
| 요청 추적과 재시도 | requestId로 단계별 기록을 연결. 재시도는 추가 부하를 만들므로 횟수·시간을 제한하고 간격을 조절 |

## 확인 문제와 피드백

### 1. 서버 분산과 세션 저장 위치

**질문:** 같은 서비스를 실행하는 A·B는 별도 프로세스이며 세션을 각자 메모리에만 저장한다. 공유 저장소·복제는 없다. 로그인 요청을 받은 A는 S7→회원 U를 저장하고 브라우저에 S7 쿠키를 설정한다. 다음 내 주문 조회는 B에 도착한다. 쿠키는 정상 전달됐고 세션도 아직 만료되지 않았지만 B에는 S7 기록이 없다. B가 로그인 상태를 확인할 수 있는지 쿠키와 세션의 역할을 구분해 설명하기. S7은 설명용 축약이다.

**사용자 답변:** 확인할 수 없다. B가 A와 세션을 공유하지 않기 때문이다. 두 서버가 세션을 함께 확인할 수 있는 구조라면 가능할 것 같다고 설명했다.

**피드백:** 결론·이유·공유 조회 구조라는 해결 방향 모두 정확하다. 쿠키는 S7을 전달할 뿐 사용자·유효성 기록 전체가 아니며 B가 조회할 대응 기록이 없다. Redis 같은 공통 저장소를 사용하도록 구성하면 어느 서버에서도 같은 세션을 조회·검증할 수 있다. 공유 저장소 접근 비용과 장애도 고려해야 한다. 단순 설치만으로 세션 공유가 자동 구현되는 것은 아니다. 구체적 구성과 운영 비용은 보충 설명이다.

### 2. 컨테이너 교체와 업로드 파일 보존

**질문:** 이미지에 없는 report.pdf를 사용자가 업로드해 컨테이너 C1의 전용 쓰기 공간 /app/uploads에만 저장했다. 외부 저장소·볼륨·백업은 없다. 배포 때 C1을 삭제하고 같은 이미지로 C2를 만들었다. 단순 중지·재시작이 아닌 삭제·재생성이다. C2에서 파일을 볼 수 있는가? 파일을 보존하려면 저장 위치를 어떻게 바꿔야 하는가?

**사용자 답변:** 볼 수 없다. C1 전용 공간을 삭제했으므로 파일도 사라졌기 때문이다. 외부 저장소나 컨테이너들이 함께 사용하는 별도 공간이 필요할 것 같다고 답했다.

**피드백:** 결과·이유·저장소 분리 방향이 정확하다. 핵심은 동시 공유 자체보다 컨테이너 삭제와 별개로 공간을 유지하는 것이다. 이름 있는 uploads-data 볼륨에 저장하고 C1만 삭제한 뒤 C2에 같은 볼륨을 연결하는 예시를 설명했다. 볼륨 자체를 삭제하면 보존되지 않으며 기본 로컬 볼륨이 다른 서버에 자동 복제되는 것도 아니다. 볼륨 재사용과 호스트 범위는 보충 설명이며 독립적으로 검증하지 않았다.

### 3. 타임아웃과 실제 주문 결과

**질문:** 0초에 주문 요청, 1초에 서버가 주문 1건 저장·커밋, 응답 지연으로 3초에 클라이언트 타임아웃, 4초에 같은 주문 재요청, 5초에 두 번째 주문도 정상 처리·커밋한다. 중복 방지·자동 취소·다른 주문·삭제는 없다. 첫 주문이 타임아웃 때문에 취소됐는지, 최종 주문 건수와 이유는?

**사용자 답변:** 첫 주문은 DB 커밋까지 되었으므로 취소됐다고 볼 수 없다. 최종 화면에 표시되는 것은 1건이지만 주문 자체는 2건 진행됐다고 답했다.

**피드백:** 첫 주문 유지와 DB 주문 총 2건은 정확하다. 화면 구현은 주어지지 않았으므로 표시가 1건이라고 단정할 수 없다. 첫 요청의 응답 수신 실패, DB의 두 주문 커밋, 화면의 표시 방식을 구분해야 한다. 타임아웃은 작업 취소나 롤백을 보장하지 않는다. 일반적으로 클라이언트가 타임아웃만 보고 서버의 처리 결과를 확정할 수 없다는 점은 보충 설명이다.

### 4. 같은 주문 재시도의 멱등성 키

**사전 설명:** 멱등성 키는 같은 업무 요청의 재시도를 식별한다. 서버가 처리 결과를 보관하고 중복 실행을 막도록 구현해야 한다. 키를 보내는 것만으로 자동 해결되지 않는다.

**질문:** 같은 사용자·같은 주문 API에서 같은 키와 동일 내용을 받으면 기존 결과를 반환하고 새 주문을 만들지 않는 서버다. K1 요청이 주문 501 생성·커밋과 결과 저장을 마쳤지만 응답이 전달되지 않았다. 기록은 유지되고 재요청은 첫 처리가 끝난 뒤 도착한다. 같은 주문 재시도에 A=K1 재사용, B=새 K2 발급 중 무엇을 선택할지, 최종 주문 건수와 이유는? 다른 주문은 없다.

**사용자 답변:** A를 선택하고 최종 주문은 1건이다. 서버가 멱등성 키로 같은 주문의 재시도를 구별했기 때문이다.

**피드백:** 선택·건수·이유가 정확하다. K1에 기록된 주문 501 결과를 반환하여 새 주문을 만들지 않는다. 별개의 주문 의도에는 새 키를 사용해야 한다. 같은 키에 다른 내용을 보내는 것은 동일 요청 재시도로 보지 않는다. 동시 요청 처리·키 기록과 업무 반영의 원자성·장애 복구 구현까지 검증한 것은 아니다. 키별 보관 기간과 동작 정책은 서비스에 따라 달라질 수 있다.

### 5. 로그의 지연 구간과 무제한 재시도

**사전 설명:** requestId는 한 요청의 여러 로그를 연결한다. 멱등성 키는 같은 업무 요청의 재시도를 식별하므로 역할이 다르다. 재시도는 일시적 오류에 도움이 될 수 있으나 추가 요청 자체가 부하를 늘린다.

**질문:** 상품 조회 R10의 두 단계가 순서대로 실행되고 그 밖의 큰 지연은 없다. 로그는 로컬 DB 상품 조회 SUCCESS 20ms, 외부 재고 API 응답 대기 TIMEOUT 3000ms다. 재고 API는 조회 전용이며 많은 사용자가 같은 타임아웃을 겪는다. 동료가 성공할 때까지 대기 간격 없이 무제한 재시도하자고 제안한다. 어느 구간을 우선 조사하며 제안에 동의하는지 요청량 관점에서 설명하기.

**사용자 답변:** 무제한 재시도는 서버에 부하를 줄 것 같아 반대했다. 로컬 DB 조회는 정상적이므로 외부 재고 API 응답 대기 로그를 우선 조사하겠다고 답했다. API 주소가 정상인지, 우리 쪽이 잘못 적었거나 데이터를 받아오는 양식에 문제가 있는지 점검이 필요할 것 같다고 설명했다.

**피드백:** 재시도 부하 판단과 우선 조사 구간이 정확하다. 이번 요청의 DB 단계는 20ms에 성공했으므로 3000ms를 기다린 외부 호출부터 조사한다. 이것만으로 DB 전반이 언제나 정상이라고 일반화하지 않는다. 주소·요청 형식은 조사 가능한 항목이지만 로그만으로 원인을 확정할 수 없다. 네트워크·연결 상태, 외부 서비스의 처리 지연·오류, 시간 제한 설정 등을 함께 확인해야 한다. 응답 형식 오류는 보통 응답을 받은 뒤 해석하는 단계이므로 응답 대기 타임아웃과 구분해 증거를 확인한다.

**재시도 보충:** 횟수와 전체 대기 시간을 제한하고, 실패가 이어질수록 재시도 간격을 늘리는 백오프를 적용할 수 있다. 여러 요청이 동시에 몰리지 않도록 간격에 무작위 차이를 주는 지터도 사용한다. 예시 간격 1초→2초→4초는 설명용이며 운영 기본값을 제시한 것이 아니다. 무제한 재시도 반대와 조사 순서는 답변으로 확인했지만 백오프·지터 설계는 보충 설명이며 독립 적용을 검증하지 않았다.
