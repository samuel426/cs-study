# SQL JOIN과 집계

- 날짜: 2026-11-10 (Asia/Seoul)
- 수업: CS-01 / 데이터베이스
- 진행: 확인 문제 5/5개 답변·피드백 완료. 숙련 완료를 의미하지 않는다.
- 목표: JOIN과 집계의 선택 이유, 중복 집계의 원인, 성능 개선을 판단할 근거를 설명하기.
- 공개 범위: 일반화한 기술 사례와 실제 학습 내용만 기록한다.

## 핵심 개념

- INNER JOIN은 연결 조건을 만족하는 양쪽 행의 조합을 반환한다. 집합의 교집합 비유만으로는 일대다 관계의 행 증가를 설명하기 어렵다.
- LEFT JOIN은 왼쪽 행을 보존하고, 오른쪽 대응 행이 없으면 결과의 오른쪽 열들을 NULL로 채운다. 원본 테이블을 수정하지 않는다. 이후 WHERE 조건에 따라 행이 제외될 수 있으므로 아래 예제에는 추가 필터가 없다.
- GROUP BY m.id는 회원별로 집계 범위를 나눈다. 그룹 안에서 신고 ID의 중복을 자동 제거하지 않는다.
- COUNT(*)는 그룹의 행 수, COUNT(r.id)는 NULL 아닌 r.id의 출현 횟수, COUNT(DISTINCT r.id)는 NULL 아닌 서로 다른 r.id의 개수다.
- COUNT 안의 DISTINCT는 해당 집계식의 대상 값에 적용한다. JOIN 결과 전체나 다른 집계식의 입력을 바꾸지 않는다.
- 조회 횟수 감소와 응답 시간 개선은 다르다. 같은 결과와 비교 조건을 확보하고 실제 시간을 확인해야 한다.

## 확인 문제와 피드백

### 1. 신고가 없는 회원도 조회하려면?

**질문:** 회원과 신고를 회원 ID로 연결한다. INNER JOIN과 LEFT JOIN의 결과 차이는 무엇이며, 신고가 0건인 회원도 관리자 화면에 보여야 할 때 회원을 왼쪽에 둔 LEFT JOIN을 선택하는 이유는?

**사용자 답변 요지:** INNER JOIN은 교집합에 해당하는 것만 연결하고 LEFT JOIN은 겹치는 값이 없어도 NULL 처리가 가능하다. INNER JOIN에서는 모든 회원이 나오지 않지만 LEFT JOIN은 신고가 없어도 회원을 조회하므로 선택한다.

**피드백:** 선택 이유는 정확하다. INNER JOIN은 조건을 만족하는 행의 조합, LEFT JOIN은 왼쪽 행을 보존하고 대응이 없는 오른쪽 열을 NULL로 채우는 것으로 표현을 보완했다. 신고가 여러 건이면 한 회원도 결과에서 여러 행이 될 수 있다.

### 2. COUNT(*)와 COUNT(r.id)의 차이

**질문:** LEFT JOIN 결과가 (A,101), (A,102), (B,NULL)이다. r.id는 신고 기본 키이며 추가 필터는 없다. 회원별로 묶었을 때 COUNT(*)와 COUNT(r.id)의 값 및 신고 건수에 적합한 식은?

**사용자 답변:** A는 2·2, B는 1·0. 행 개수가 아니라 회원의 신고 건수를 세어야 하므로 COUNT(r.id)를 사용한다.

**피드백:** 값과 선택 이유가 모두 정확하다. B의 보존 행은 COUNT(*)에 포함되지만 NULL인 신고 ID는 COUNT(r.id)에 포함되지 않는다. 이 사례에서는 구분했지만 문제 5에서 NULL 처리를 다시 혼동했으므로 안정적인 숙련으로 보지 않는다.

### 3. 두 일대다 관계를 함께 연결하면?

**질문:** A의 신고 ID는 101·102, 로그인 ID는 201·202·203이다. 각 id는 기본 키다. 아래 쿼리에서 A의 report_count와 이유는?

```sql
SELECT m.id, COUNT(r.id) AS report_count
FROM members m
LEFT JOIN reports r ON r.member_id = m.id
LEFT JOIN login_history l ON l.member_id = m.id
GROUP BY m.id;
```

**사용자 답변 요지:** 5. 신고와 로그인 이력이 각각 회원 A에 건수별로 붙을 것 같다.

**피드백:** 둘 다 A에 연결된다는 점은 맞지만 행 수를 더하는 것으로 생각했다. 각 신고에 로그인 세 건이 모두 대응하므로 2 × 3 = 6행이다. 신고 ID가 각각 세 번씩 등장하고 NULL이 아니므로 COUNT(r.id)는 6이다.

**보충 설명:** COUNT(DISTINCT r.id)를 사용하면 이 예제의 서로 다른 신고 ID 두 개를 센다. 각 이력을 회원별로 먼저 집계한 뒤 연결하는 방법도 설명했다. 모든 JOIN의 행 수가 무조건 원본 행 수의 곱이라는 뜻은 아니며, 이 사례의 회원 ID 연결 조건에 따른 결과다. 사전 집계 적용 능력은 확인하지 않았다.

### 4. 조회 횟수를 줄이면 성능 개선일까?

**질문:** SQL 실행을 7회에서 4회로 줄이고 일부 조회를 JOIN으로 합쳤다. 이 사실만으로 성능이 좋아졌다고 단정할 수 있는가? 이유와 추가로 확인하거나 측정할 내용은?

**사용자 답변 요지:** 단정할 수 없다. 테이블 구조나 데이터가 앞으로 붙으며 어떻게 확장될지 모른다. 열의 의미, 조회 방식과 걸리는 시간을 확실히 알아야 한다.

**피드백:** 횟수만으로 단정하지 않고 시간 확인을 언급한 방향은 맞다. 미래 데이터 증가뿐 아니라 현재 데이터에서도 JOIN의 처리 행 수와 집계 비용이 늘어 느려질 수 있다. 열의 의미는 결과 정확성에 중요하지만 속도 개선의 직접 근거는 아니다.

**보충 설명:** 같은 결과·데이터·환경·동시 요청 수와 비슷한 캐시 조건에서 변경 전후를 여러 번 비교한다. API 응답 시간과 DB 실행 시간을 구분한다. EXPLAIN은 실행 계획을, EXPLAIN ANALYZE는 쿼리를 실제 실행하며 시간·행 수 등을 보여준다. 구체적인 측정 방법과 실행 계획 해석은 설명만 했으며, 사용자가 실제로 측정했거나 성능 개선을 입증했다고 기록하지 않는다.

### 5. 중복과 NULL을 함께 복습하기

**질문:** A의 신고 ID는 101·102·103, 로그인 ID는 201·202다. B는 신고가 없고 로그인 ID 203만 있다. 각 id는 기본 키다. 회원을 기준으로 두 테이블을 각각 회원 ID만으로 LEFT JOIN하고 회원별로 묶는다. 추가 필터는 없다. 각 회원의 COUNT(r.id)와 COUNT(DISTINCT r.id), A의 반복 이유와 B의 값이 그렇게 나오는 이유는?

**사용자 답변:** A는 6·3, B는 1·1. 틀렸을 것 같고 DISTINCT가 어디까지 영향을 미치는지 감이 오지 않는다. 이유도 모르겠으니 설명을 요청했다.

**피드백:** A의 숫자 6·3은 맞지만 원리는 직접 설명하지 못했다. B는 0·0이다. 다음 표로 JOIN 결과를 펼쳤다.

| 회원 | 신고 ID r.id | 로그인 ID l.id |
|---|---|---|
| A | 101 | 201 |
| A | 101 | 202 |
| A | 102 | 201 |
| A | 102 | 202 |
| A | 103 | 201 |
| A | 103 | 202 |
| B | NULL | 203 |

A 그룹의 r.id 값은 [101,101,102,102,103,103]이다. COUNT(r.id)는 여섯 출현을 세고 COUNT(DISTINCT r.id)는 서로 다른 101·102·103을 센다. B 그룹의 r.id 값은 [NULL]이다. COUNT(r.id)와 COUNT(DISTINCT r.id) 모두 NULL을 세지 않아 0이다. B에 대해 1이 되는 식은 COUNT(*)이며, 로그인 ID 203이 있다고 신고 ID가 생기는 것은 아니다.

**DISTINCT의 적용 범위 보충:** GROUP BY m.id로 나눈 각 회원 그룹 안에서, COUNT(DISTINCT r.id)는 r.id만을 대상으로 중복을 제외한다. 같은 SELECT의 COUNT(*)나 COUNT(r.id)는 그대로 원래 그룹을 대상으로 계산한다. NULL 하나가 남아 있으니 1로 세는 방식이 아니다. SELECT DISTINCT로 출력 열 조합의 중복을 제거하는 경우와도 구분해야 한다. 이는 논리적인 설명이며 DB가 내부적으로 반드시 이 순서대로 물리 실행한다는 뜻은 아니다.

**확인 범위:** 설명 후 재답변은 받지 않았다. DISTINCT의 범위, NULL 제외와 행 조합 원리를 이해했다고 확정하지 않는다.

## 복습 포인트와 다음 학습

- 확인한 내용: LEFT JOIN을 선택하는 요구사항, 단순 사례의 COUNT 구분, 조회 횟수만으로 성능 개선을 단정할 수 없다는 판단.
- 계속 복습할 내용: COUNT(*)와 COUNT(열)의 NULL 처리, 회원별 COUNT(DISTINCT 열)의 적용 범위, 두 일대다 JOIN에서 행이 반복되는 이유.
- 보충 설명만 한 내용: 사전 집계, 실행 계획, 같은 조건에서의 성능 비교 절차.
- 다음 기본 주제: 인덱스와 조회 성능. 총 5문제 중 첫 문제에 위 약점 복습을 포함한다. 오늘 추가 확인 문제는 내지 않는다.
- 사용자가 설명을 더 요청하면 같은 수업의 보충 설명으로 이어가고 별도 수업 완료로 세지 않는다.
