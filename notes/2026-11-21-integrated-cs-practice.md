## 핵심 개념

| 개념 | 이번에 구분한 내용 |
|---|---|
| GROUP BY | 지정한 열의 값이 같은 행을 그룹으로 묶음. 행 전체의 중복 여부와 다름 |
| COUNT | COUNT(*)는 행 수, COUNT(열)은 NULL이 아닌 값 수, COUNT(DISTINCT 열)은 NULL을 제외한 서로 다른 값 수 |
| 복합 B-tree 인덱스 | 선행 열의 동등 조건과 다음 열의 범위 조건으로 연속된 탐색 구간을 좁힐 수 있음. 실제 성능은 계획·측정으로 확인 |
| 가상 주소 변환 | 가상 주소를 페이지 번호와 오프셋으로 나누고 페이지 테이블로 프레임을 찾아 같은 오프셋을 더함 |
| 서명과 암호화 | 서명은 신뢰하는 발급자의 서명과 내용 변조 여부 검증, 암호화는 내용의 기밀성 보호 |
| 변조와 탈취 | 내용을 바꾸면 기존 서명 검증이 실패하지만 유효한 토큰 전체를 그대로 재사용하면 서명만으로 탈취를 감지할 수 없음 |
| 트랜잭션과 락 | 작업을 함께 반영·취소하는 범위와 동시 접근 보호 범위를 구분. 서로 다른 JVM의 객체 락은 공유되지 않음 |
| FOR UPDATE | 조회한 DB 행에 잠금을 획득. 이번 예제에서는 트랜잭션 커밋 또는 롤백까지 유지 |

## 확인 문제와 피드백

### 1. JOIN 결과의 COUNT·NULL·DISTINCT

**질문:** 회원·신고·로그인 이력을 LEFT JOIN한 결과가 아래와 같다. 신고 ID 하나는 실제 신고 한 건을 뜻한다. 회원별 GROUP BY 후 COUNT(*), COUNT(r.id), COUNT(DISTINCT r.id)의 값과 실제 신고 건수에 맞는 식·이유는?

| 회원 | 신고 ID r.id | 로그인 ID l.id |
|---|---|---|
| A | 11 | 201 |
| A | 11 | 202 |
| A | 12 | 201 |
| A | 12 | 202 |
| B | NULL | 301 |

**사용자 답변:** 겹치는 것이 없으므로 GROUP BY를 해도 크게 바뀌지 않을 것 같다고 물었다. A=4,4,2와 B=1,0,0을 답했고 신고 ID를 중복 없이 세기 위해 COUNT(DISTINCT r.id)를 선택했다.

**피드백:** 여섯 값과 선택·중복 제거 이유 모두 정확하다. GROUP BY는 행 전체가 같은지 확인하는 것이 아니라 지정한 회원 값으로 묶는다. A의 네 행과 B의 한 행을 각각 집계하여 결과는 회원별 두 행이 된다. A의 신고 ID [11,11,12,12]에서 서로 다른 값은 11·12이며 B의 [NULL]은 열 값 집계에서 제외한다. 마지막 식 안의 DISTINCT가 다른 COUNT 식의 값까지 줄이지는 않는다. 그룹 기준과 DISTINCT 적용 범위는 보충 설명이며 독립적인 재답변으로 검증하지 않았다.

### 2. 복합 인덱스 순서와 조회 범위

**질문:** 회원 100만 명의 주문이 섞인 orders에서 한 회원의 주문은 전체의 작은 일부다. 아래 조회를 자주 실행할 때 일반적인 B-tree 인덱스 A=(member_id, created_at), B=(created_at, member_id) 중 무엇을 우선 검토하며 범위를 어떻게 좁히는가?

```sql
SELECT *
FROM orders
WHERE member_id = 42
  AND created_at >= '2026-11-01'
  AND created_at < '2026-12-01';
```

**사용자 첫 답변:** B를 선택했다. 회원이 100만 명이므로 특정 회원을 먼저 찾기보다 한 달 주문으로 줄인 뒤 그 안에서 회원을 찾는 것이 빠를 것 같다고 설명했다.

**피드백:** 범위를 줄이려는 접근은 타당하지만 회원 수만으로 날짜 선행이 유리하다고 판단할 수 없다. 회원 ID 인덱스 탐색은 회원을 한 명씩 확인하는 방식이 아니다. 정렬된 트리의 분기 정보를 따라 목표 구간을 찾는다. A는 (회원 42, 11월 시작)으로 이동하여 회원 42의 11월 구간을 연속해서 읽기 적합하다. 먼저 해당 회원의 모든 과거 주문을 읽어야 하는 것도 아니다. B는 날짜별로 여러 회원 주문이 섞이므로 날짜 범위에서 회원 조건을 추가 확인해야 할 수 있다. 다른 열 순서가 절대 사용 불가능하거나 실제 속도가 반드시 느리다고 일반화하지 않는다.

**같은 문제의 보충 확인:** A에서 회원 42의 11월 시작 위치를 찾기 위해 회원 100만 명을 한 명씩 확인해야 하는지, 앞선 판단을 어떻게 바꿀지 물었다.

**보충 후 사용자 답변:** 그럴 필요 없이 B-tree의 정렬된 값을 기준으로 분기별 탐색 범위를 좁히면 된다고 설명했다.

**확인 범위:** 설명 후 정렬·분기를 통한 탐색 원리를 확인했다. 새로운 쿼리에 대한 독립적인 복합 인덱스 선택이나 실제 실행 계획 해석은 미검증이다. WHERE 조건의 작성 순서와 인덱스 열 순서는 다르다.

### 3. 새 숫자의 페이지·오프셋·물리 주소 계산

**질문:** 교육용 페이지·프레임 크기는 32바이트이고 주소·번호는 0부터 시작한다. P·Q가 가상 주소 77에 접근한다. 모든 페이지는 RAM에 있고 접근 가능하다. 아래 대응에서 가상 페이지 번호·오프셋·P와 Q의 물리 주소 및 차이의 이유는?

| 가상 페이지 | P의 프레임 | Q의 프레임 |
|---|---|---|
| 0 | 4 | 6 |
| 1 | 1 | 3 |
| 2 | 5 | 9 |

**사용자 답변:** 페이지 번호 2, 오프셋 13, P 물리 주소 173, Q 물리 주소 301이다. 각자의 물리 프레임 번호가 달라 계산 결과가 달라진다.

**피드백:** 새 숫자의 네 값과 프레임 대응 차이라는 이유가 정확하다. 77=2×32+13, P=5×32+13, Q=9×32+13으로 정리했다. 각 프로세스의 페이지 테이블이 같은 가상 페이지를 서로 다른 프레임에 연결하며 오프셋은 유지된다고 표현을 보완했다. 이전에 미검증이던 새 사례 계산을 이 범위에서 확인했다. 실제 페이지 크기·페이지 폴트·페이지 테이블 구현까지 확인한 것은 아니다.

### 4. JWT 서명·암호화·원본 보관과 탈취

**질문:** 암호화 없이 서명만 한 JWT를 사용한다. 동료가 서명이 있으므로 내용을 읽을 수 없고, 위조 확인을 위해 서버가 발급한 모든 JWT 원본을 저장해 받은 토큰과 비교해야 한다고 설명한다. 두 주장에 동의하는지, 서명의 역할과 검증 방법을 자신의 말로 설명하기.

**사용자 첫 답변:** 내용을 읽지 못하더라도 공격자가 데이터를 가져가 서명을 사용할 위험이 있다고 지적했다. 원본 토큰 저장·비교는 말이 안 되는 것 같고 JWT를 암호화해야 한다고 답했다. 두 주장에 동의하지 않으며 서명은 서버가 검증하는 일을 한다고 설명했다.

**피드백:** 탈취 후 재사용 위험을 떠올린 점은 타당하다. 그러나 내용 열람·변조·탈취 재사용과 서명·암호화의 역할이 혼재했다. 서명만 한 JWT는 읽을 수 있다. 서명은 신뢰하는 발급자의 서명과 내용 변조 여부를 검증하며 내용을 숨기지 않는다. 비대칭 서명 예시에서는 발급자의 개인키로 서명하고 서버가 미리 신뢰하도록 설정한 공개키로 받은 내용과 서명을 검증한다. 이는 모든 JWT가 같은 키 방식을 쓴다는 뜻이 아니다. 모든 원본 토큰의 보관·대조는 서명 검증의 필수 조건이 아니지만 폐기 관리 등 별도 목적의 서버 기록은 가능하다.

**추가 설명:** USER를 ADMIN으로 바꾼 뒤 기존 서명을 보내면 검증에 실패한다. 유효한 Bearer 토큰 전체를 그대로 탈취한 경우 서명 자체는 유효하므로 서명 검증만으로 탈취 여부를 판별할 수 없다. 암호화된 증표도 전체를 그대로 재사용할 수 있어 내용 암호화만으로 해결되지 않는다. 전송·보관 중 노출 방지, 만료·폐기, 발급자·대상·권한 검증은 따로 고려한다.

**같은 문제의 보충 확인:** 공격자는 서명 키를 모르고 서버는 올바르게 서명 검증한다. A는 USER를 ADMIN으로 바꾸고 기존 서명을 보내며 B는 유효한 다른 사람의 토큰 전체를 아무 변경 없이 보낸다. 서명 검증이 실패하는 쪽과 이유는?

**보충 후 사용자 답변:** A는 USER의 서명이 ADMIN으로 바꾼 내용의 검증을 성공시키도록 만들어진 것이 아니므로 실패한다. B는 유효한 토큰 전체를 훔쳐 그대로 보내면 본인이 아니어도 당시 조회한 정보나 기능의 응답을 받을 수 있을 것 같다고 답했다.

**최종 피드백:** 내용·서명 불일치와 탈취 토큰 재사용을 구분했다. ADMIN이라는 단어 자체를 금지하는 것이 아니라 서명된 내용과 달라졌기 때문이다. B가 받는 응답은 과거 응답의 복사본이 아니라 요청 시점의 권한·데이터·검증 결과에 따른다. 같은 예제의 설명 후 구분을 확인했으며 원본 보관 없이 검증하는 키 절차를 독립적으로 설명한 것은 아니다.

### 5. 두 서버의 재고 경쟁과 보호 범위

**질문:** 서로 다른 JVM의 서버 A·B가 같은 DB에서 재고 1개인 상품에 대한 서로 다른 두 사용자의 주문을 처리한다. 같은 주문의 재시도가 아니다. 각 요청은 재고 조회→1개 이상 확인→읽었던 값에서 1을 뺀 재고 저장→주문 저장→커밋을 하나의 트랜잭션으로 처리한다. 일반 SELECT로 둘 다 재고 1을 읽을 수 있고 별도 동시성 검증이나 FOR UPDATE 조회는 없다. 동료 1은 트랜잭션만으로 충분하다고, 동료 2는 각 JVM의 별도 락을 쓰는 synchronized로 두 서버 사이 경쟁도 해결된다고 말한다. 충분한지, 공통 보호 대상과 처리 방향을 제안하기. 이전 DB 행 잠금을 떠올려도 된다고 안내했다.

**사용자 답변:** 부족하며 DB에서 FOR UPDATE 잠금 조회가 필요하다고 답했다. 공통 보호 대상은 재고 수량이라고 설명했다. 제시된 로직의 주문 저장까지 잠가야 할 것 같지만 커밋까지 잠기는지 헷갈린다고 질문했다.

**피드백:** 공통 DB의 재고 행을 보호하고 잠금 조회를 사용하자는 방향은 정확하다. 잠기는 것은 코드 구간이 아니라 조회한 DB 행이며, 이번 일반적인 트랜잭션 흐름에서 잠금은 커밋 또는 롤백까지 유지된다. FOR UPDATE가 이후 실행할 모든 코드·주문 테이블 전체를 미리 잠근다는 뜻은 아니다. 주문 저장에도 필요한 DB 잠금이 따로 발생할 수 있지만 여기서 경쟁을 조정하는 대상은 같은 상품의 재고 행이다.

```text
트랜잭션 시작
→ 재고 행을 SELECT ... FOR UPDATE로 조회하며 잠금 획득
→ 조회한 최신 재고가 1개 이상인지 확인
→ 재고 차감
→ 주문 저장
→ COMMIT 또는 ROLLBACK에서 잠금 해제
```

**실행 예시 보충:** 일반적인 READ COMMITTED 조건에서 두 요청이 모두 같은 방식으로 잠금 조회하면 A가 재고 행을 잠근 동안 B의 같은 행 FOR UPDATE는 기다린다. A가 재고를 0으로 만들고 주문을 커밋하면 B는 갱신된 재고 0을 확인하고 주문을 거부한다. 일반 SELECT까지 모두 막는다는 뜻은 아니며 격리 수준에 따라 충돌 시 재시도할 오류가 날 수도 있다. 자동 커밋으로 잠금 조회만 끝내지 않고 검사·차감·주문 저장까지 같은 트랜잭션에 포함해야 한다.

**두 제안 보완:** 트랜잭션으로 묶는 것은 주문·재고를 함께 반영·취소하는 데 필요하지만 제시된 동시 읽기 경쟁을 자동으로 해결하지 않는다. synchronized는 같은 JVM에서 같은 락을 사용하는 실행 흐름을 조정하며 두 서버의 별도 락으로 공통 DB 경쟁을 조정하지 못한다. 이 설명과 커밋까지의 잠금 수명은 보충이며 사용자가 독립적으로 설명한 것으로 기록하지 않는다. FOR UPDATE는 가능한 해결책 중 하나이며 모든 시스템의 유일한 해법은 아니다.

- 우선 복습: 복합 인덱스의 열 순서·연속 구간, JWT 서명·암호화와 검증 키 역할, DB 행 잠금 대상·커밋 경계와 JVM 락 범위.
- 추가 복습 후보: GROUP BY 기준과 DISTINCT 범위, HashMap 조회 비용·저장량·GC, 쿠키·세션 역할, HTTPS와 인가 구분. 기본 5문제 안에서 우선순위를 조정한다.
