| 개념 | 설명 |
|---|---|

## 확인 문제와 피드백

### 1. 변수 두 개와 리스트 객체의 수 · 11월 14일

**질문:** 아래 출력값은 무엇이며 a와 b가 같은 리스트를 가리키는가? 이유를 설명한다.

```java
ArrayList<String> a = new ArrayList<>();
ArrayList<String> b = a;
b.add("hello");
System.out.println(a.size());
```

**사용자 답변 요지:** 헷갈리지만 같은 리스트 같다. b도 new로 만들어야 서로 다른 리스트가 될 것 같다.

**피드백:** 같은 객체를 참조한다는 판단과 별도 객체 생성 방향이 정확하다. b=a는 객체 복사가 아니라 참조 값의 복사이며 출력은 1이다. b를 new ArrayList<>()로 초기화하면 별도 빈 리스트를 만들어 같은 추가 코드에서 a.size는 0이다. 출력 숫자 자체는 사용자가 직접 답하지 않아 보충 설명으로 구분한다.

### 2. 메서드가 반환한 리스트의 수명 · 11월 14일

**질문:** makeList가 끝나면 그 호출의 프레임과 local은 사라진다. result.size는 정상 출력되는가, 리스트도 사라지는가? 지역 변수와 객체를 구분해 설명한다.

```java
static ArrayList<String> makeList() {
    ArrayList<String> local = new ArrayList<>();
    local.add("hello");
    return local;
}

public static void main(String[] args) {
    ArrayList<String> result = makeList();
    System.out.println(result.size());
}
```

**사용자 답변:** “정상적으로 출력될거 같아 return local이 ArrayList 받는거라”.

**피드백:** 정상 사용 판단은 맞다. return local은 리스트 객체의 참조 값을 반환하며 result가 이를 받는다. local의 수명이 끝나도 같은 객체를 result로 계속 사용할 수 있고 출력은 1이다. 객체 복사나 지역 변수 자체의 이동은 아니다. 반환 타입만으로 객체 수명을 설명하기는 부족하며 구체적인 참조 전달·스택과 힙 구분은 보충 설명이다.

### 3. 한 변수에 null을 대입하면? · 11월 14일

**질문:** a=null 때문에 리스트가 회수되어 뒤의 사용이 실패하는가? 출력과 이유를 설명한다.

```java
ArrayList<String> a = new ArrayList<>();
ArrayList<String> b = a;
a = null;
b.add("hello");
System.out.println(b.size());
```

**사용자 답변 요지:** 실패하지 않는다. b가 a의 ArrayList를 가리키는 값을 가지고 있어 정상적으로 출력될 것 같다.

**피드백:** 정상 사용과 b의 참조가 남는다는 이유가 정확하다. a=null은 a의 값만 바꾸며 b의 참조를 바꾸지 않는다. b로 후속 사용이 가능하고 출력은 1이다. 숫자 자체는 보충 설명이다. 객체의 도달 가능성과 변수 하나의 null 여부를 구분한다.

### 4. 계속 유지하는 cache와 GC · 11월 14일

**질문:** 서버가 실행 중 계속 유지하고 조회할 수 있는 cache에 요청마다 새 배열을 추가하며 제거하지 않는다. handleRequest 종료로 지역 data가 없어지면 배열도 GC로 회수할 수 있는가? 요청이 계속 오면 메모리 사용은 어떻게 되는가? 동시성 문제는 배제한다.

```java
static final ArrayList<byte[]> cache = new ArrayList<>();

static void handleRequest() {
    byte[] data = new byte[1024 * 1024];
    cache.add(data);
}
```

**사용자 답변 요지:** 회수하지 못할 것 같다. cache는 계속 사용되는 ArrayList이고 데이터가 cache 안에 있어서 GC가 빼내기 어려워 보인다.

**피드백:** 회수 불가 판단과 cache에 참조가 남는다는 핵심은 맞다. 꺼내기 어려워서가 아니라 cache를 통해 배열에 계속 접근할 수 있어 회수 대상이 아니다. 지역 data가 없어져도 cache가 보관한 참조는 남는다.

**보충 설명:** 요청마다 약 1MB의 배열과 부가 메모리가 누적된다. 한정된 힙에서 계속 추가하면 OutOfMemoryError가 발생할 수 있다. 보관량 제한·삭제 정책으로 불필요한 참조를 정리해야 하고 다른 참조도 없어져야 배열이 회수 대상이 된다. 실제 회수 시점은 즉시 보장되지 않는다. 사용자가 메모리 증가와 해결 정책까지 직접 설명한 것으로 기록하지 않는다.

### 5. ID 조회를 위한 컬렉션과 메모리 한계 · 11월 15일

**질문:** 회원 10만 명을 저장하고 중복되지 않는 회원 ID로 한 명을 반복 조회한다. ID 정렬·별도 인덱스 없는 ArrayList<User>와 ID를 key로 쓰는 HashMap<Long, User> 중 무엇을 선택하고 왜인가? 저장 순서는 필요 없고 한 스레드에서 처리하며 해시가 잘 분산된다고 가정한다. HashMap으로 바꾸기만 하면 새로운 ID의 회원을 끝없이 추가해도 메모리 문제가 해결되는가?

**사용자 답변 요지:** HashMap을 선택하겠다. key를 찾을 때 “log 1”이 드는 것으로 알고 있다. 새 회원을 끝없이 추가할 때 메모리 문제가 해결되는지는 모르겠다.

**피드백:** 선택은 적절하다. 정확한 표현은 평균 O(1), 즉 평균적인 상수 시간 조회다. log 1이나 O(log n)과 구분한다. O는 입력 크기에 따른 연산량 증가를 표현하는 표기이며 O(1)은 명령을 정확히 한 번 실행한다는 뜻이 아니다. 해시가 잘 분산된다는 조건이 필요하며 항상 같은 실제 실행 시간을 보장하지 않는다.

ArrayList에서 위치 번호를 알면 get(index)는 O(1)이지만 이 문제는 회원 ID로 해당 위치를 찾아야 한다. 정렬·별도 인덱스가 없는 목록을 순차 탐색하면 최악에 n명을 확인하므로 O(n)이다. 예제 조건에서는 ID를 key로 쓰는 HashMap이 반복 조회에 적절하다.

**메모리 보충 설명:** 조회 비용과 저장량은 별개다. HashMap도 새 ID와 회원 객체에 대한 참조를 계속 저장하면 메모리 사용이 증가한다. 지속적으로 도달 가능한 map이 회원 객체를 붙잡고 있으면 GC가 임의로 제거하지 않는다. 회원당 크기가 비슷하다는 조건에서 저장량은 회원 수에 비례해 늘며 자동 만료·보관량 제한도 기본 HashMap이 제공하는 기능이 아니다. 필요한 데이터를 DB에 보관하고 메모리에는 제한된 캐시를 두는 등의 별도 설계가 필요하다. 이 해결 방법과 복잡도 구분은 설명 후 재답변이 없어 미검증이다.

## 확인된 내용과 다음 복습

- 확인: 같은 객체를 참조한다는 판단과 별도 new 생성 방향, 메서드 반환 후 리스트 사용 가능 판단, a=null 이후 b의 참조가 남는다는 이유, cache에 남은 배열의 회수 불가 판단, ID 조회용 HashMap 선택.
- 복습 필요: 메서드 반환이 참조 값을 전달한다는 원리, 스택 프레임과 힙 객체 수명 구분, GC의 도달 가능성 표현, O(1)과 O(log n) 구분, 빠른 조회와 저장량 제한의 차이.
- 설명만 한 내용: 정확한 출력 숫자, cache 누적으로 인한 메모리 증가와 삭제 정책, HashMap 조회 복잡도의 조건과 공간 사용. 실제 코드 실행·성능 측정·JVM 메모리 분석을 했다고 기록하지 않는다.
- 범위: JVM 역할은 소개만 했다. 클래스 로딩·JIT·GC 알고리즘과 튜닝은 학습하거나 검증하지 않았다.
