# Redis 요청 제한

- 날짜: 2026-11-14 (Asia/Seoul)
- 수업: CS-04 / Redis·동시성
- 진행: 확인 문제 5/5개 답변·피드백 완료. 정답 5개 또는 숙련 완료라는 뜻은 아니다.
- 계획상 11월 13일 주제를 실제 학습일인 14일에 진행했다. 같은 날 Java 수업 5문제를 이어서 진행할 예정이며 이 기록에는 포함하지 않는다.
- 목표: 요청별 기록, 최근 시간 구간의 요청 수, 동시 요청의 보호 범위와 key 만료의 역할을 설명하기.
- 예제는 일반적인 학습 사례이며 실제 서비스의 구현·측정 결과가 아니다.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| Redis key | 저장된 값을 찾는 이름. 예제의 requests:A는 사용자 A의 요청 기록 보관함을 가리킴 |
| Sorted Set | 고유한 member와 정렬 기준인 숫자 score를 함께 보관하는 자료구조 |
| member | 집합 안의 항목을 구별하는 값. 요청 횟수를 기록하려면 요청마다 고유한 ID를 사용 |
| score | 정렬 기준. 이 예제에서는 요청 시각이며 서로 다른 member의 score는 같아도 됨 |
| 기본 ZADD | 새 member면 추가하고 이미 있는 member면 score를 갱신. 명령의 별도 옵션은 다루지 않음 |
| 최근 시간 구간 | 현재 시각을 기준으로 이동하는 구간. 예제는 현재-60초 초과, 현재 이하로 경계를 정함 |
| 동시 요청 보호 | 유효 요청 수 확인→한도 판단→허용할 요청 기록 사이에 다른 요청이 끼어들지 않도록 보호 |
| TTL | Time To Live, 만료까지 남은 시간. EXPIRE로 설정하는 key의 만료와 Sorted Set 안의 개별 요청 시각은 다름 |

Sorted Set의 score는 숫자다. 그 숫자를 요청 시각으로 해석하는 것은 애플리케이션의 설계이며 Redis가 score만 보고 각 항목을 자동 만료시키지는 않는다.

## 확인 문제와 피드백

### 1. 커밋과 업무 규칙 복습

**질문:** A 4만 원, B 2만 원에서 A가 B에게 5만 원을 송금한다. 업무 규칙은 잔액이 음수가 되면 안 된다는 것이지만 코드의 잔액 검사와 DB 제약이 없고 잔액 열은 음수를 저장할 수 있다. 차감과 입금이 한 트랜잭션에서 성공해 커밋됐다. 최종 잔액과 업무 규칙 준수 여부는?

**사용자 답변:** A는 -1만 원, B는 7만 원. 커밋만으로 업무 규칙까지 지켰다고 할 수 없다.

**피드백:** 계산과 판단이 정확하다. 이전 수업에서 규칙이 자동 적용된다고 본 답변을 이번 사례에서 바로잡았다. 원자성은 전부 반영 또는 전부 취소를 보장하며 잔액 규칙을 자동으로 만들어 주지 않는다. 검증·제약을 실제로 구현해야 한다는 구체적인 이유는 보충 설명이다. 원자성 정의와 검증 구현까지 사용자가 설명했다고 기록하지 않는다.

### 2. 같은 member와 요청별 member

**질문:** 비어 있는 사용자 A의 Sorted Set에 서로 다른 요청 3건을 기본 ZADD로 순서대로 넣는다. score는 각각 1000ms, 1000ms, 1500ms다. 방식 ①은 세 요청 모두 member=user-A, 방식 ②는 각각 req-1, req-2, req-3을 사용한다. 삭제·만료는 없다. 각 방식의 최종 항목 수와 요청 횟수를 정확히 세는 선택 및 이유는?

**사용자 반응과 답변:**

- 처음에는 문제가 아예 이해되지 않는다고 설명을 요청했다.
- 두 요청까지의 중간 상태를 설명한 뒤에는 “3개? 모르겠어”라고 답했다. 어느 방식에 대한 답인지 명시하지 않았다.
- 정답과 갱신 과정을 설명한 뒤 방식 ①이 한 항목인 이유를 다시 물었다. 사용자는 “user-A라는 key 하나에 value만 바뀐거(업데이트?)라고 생각해”라고 답했다.

**피드백과 보충:** 방식 ①은 같은 member를 갱신하므로 최종 user-A:1500 한 항목이다. 방식 ②는 서로 다른 member이므로 세 항목이 남아 요청 횟수를 셀 수 있다. 같은 요청 시각이라고 같은 요청인 것은 아니다.

| 구분 | 방식 ① | 방식 ② |
|---|---|---|
| 첫 요청 후 | user-A:1000 | req-1:1000 |
| 두 번째 요청 후 | user-A:1000 | req-1:1000, req-2:1000 |
| 세 번째 요청 후 | user-A:1500 | req-1:1000, req-2:1000, req-3:1500 |

같은 기록이 갱신된다는 동작은 최종 답변에서 확인했다. 다만 user-A는 Redis key가 아니라 집합 내부의 member다. 두 방식 모두 key는 requests:A처럼 사용자별 보관함을 찾는 이름이고 그 값 전체가 Sorted Set이다. key/member/score 구분은 보충 설명 후 새 사례에서 검증하지 않았다. 중간 설명과 이유 재확인은 같은 문제 2 안의 진행이며 별도 문제로 세지 않는다.

### 3. 최근 요청 수와 새 요청의 허용 여부

**질문:** 현재 시각은 120초이고 기존 요청 시각은 50초, 80초, 110초다. 최근 60초에 새 요청까지 포함해 최대 3회를 허용하며 구간은 60초 초과~120초 이하로 정한다. 120초에 새 요청 하나가 왔고 다른 동시 요청은 없다. 기존 유효 요청 수와 새 요청 허용 여부 및 이유는?

**사용자 답변:** “3건, 요청을 몇개까지 허용할 수 있는지 정했는지에 따라 다를거 같은데?”

**피드백:** 허용 여부를 판단하려면 최대 횟수가 필요하다는 일반적인 판단은 맞다. 이 문제에서는 이미 최대 3회라고 정했다. 50초 기록은 70초 전이므로 제외하고 80초·110초 두 건만 센다. 새 요청까지 포함하면 3건이므로 허용한다.

사용자의 3건이 기존 건수인지 새 요청 포함 수인지 명시되지 않아 단정하지 않는다. 두 수의 구분과 구간 적용을 설명했다. 이후 문제 5에서 같은 시각 사례의 최근 요청 수 2건은 맞혔으나 새 경계 사례까지 검증한 것은 아니다.

### 4. 두 요청이 같은 건수를 먼저 읽는 경우

**질문:** 최근 60초에 최대 3회 허용하며 현재 유효한 요청은 2건이다. 같은 사용자의 새 요청 X·Y를 다음 순서로 처리한다. 그동안 기존 요청은 구간에서 빠지거나 삭제·만료되지 않으며 X·Y의 member는 서로 다르다. 최종 건수와 규칙 준수 여부 및 이유는?

```text
X: 기존 2건 확인 → 허용 가능하다고 판단
Y: 기존 2건 확인 → 허용 가능하다고 판단
X: 요청 기록 추가 후 허용
Y: 재확인 없이 요청 기록 추가 후 허용
```

**사용자 답변:** 최종 4건이며 최대 3회 규칙을 지키지 못했다. X가 끝날 때까지 Y가 기다려야 하는데 Y가 먼저 조회를 시작했기 때문이다.

**피드백:** 건수, 규칙 위반, 같은 과거 건수를 먼저 읽은 원인과 보호 방향이 정확하다. 보호할 범위는 요청 처리 전체가 아니라 해당 사용자의 유효 건수 확인→한도 판단→허용할 요청 기록까지다. 이 구간을 묶으면 X가 2건을 읽고 기록한 후 Y는 3건을 읽어 거절할 수 있다.

**보충 설명:** Lua 스크립트는 Redis 서버 안에서 실행하는 프로그램이며 실행 중 다른 클라이언트 명령이 끼어들지 않게 조건 판단과 기록을 묶을 수 있다. 이 설명은 실행 중 끼어들기 방지에 관한 것으로, 관계형 DB의 실패 시 전체 롤백 보장과 동일시하지 않는다. 실제 스크립트 작성, 오류 처리, 장애 복구는 이 수업에서 구현하거나 검증하지 않았다.

### 5. key 만료와 최근 시간 구간

**질문:** A의 요청 기록 key에 req-1:50초, req-2:80초, req-3:110초가 들어 있다. 110초 시점에 이 key에 EXPIRE 60을 설정하여 만료 시각은 170초다. 이후 추가·삭제·만료 갱신은 없고 현재는 120초다. 최근 60초에 해당하는 요청 수는? TTL 설정 때문에 50초 기록이 지금 자동으로 사라졌다고 볼 수 있는가? 이유는?

**사용자 답변:** 2건이고 사라졌다고 봐도 될 것 같다. 현재 120초이며 req-1은 110초에 만료될 것 같기 때문이다.

**피드백:** 최근 구간의 요청 수 2건은 정확하다. 하지만 req-1에 개별 60초 만료를 설정한 것이 아니다. 50+60=110초를 req-1의 만료 시각으로 계산할 수 없다. 실제 설정은 110초에 보관함 전체의 만료를 60초 뒤로 정했으므로 170초에 key 전체가 만료된다. 120초에는 기록 3개가 모두 남아 있고 최근 구간에 맞는 2개만 세어야 한다.

| 120초 시점의 구분 | 건수 |
|---|---:|
| 실제 저장된 항목 전체 | 3 |
| 최근 60초에 해당하는 항목 | 2 |

**보충 설명:** 오래된 기록을 score 기준으로 삭제한 뒤 남은 수를 세거나, 필요한 score 범위만 골라 세는 방법이 있다. key 만료는 보관함 전체의 수명 관리이며 그 자체가 최근 구간의 요청 수 계산을 대신하지 않는다. 이 설명 후 재답변은 없으며 TTL 구분을 숙련했다고 기록하지 않는다.

- 복습 필요: key/member/score 구분, 기존 요청 수와 신규 포함 수, key TTL과 개별 기록의 시각 구분, 보관된 기록과 집계 대상 기록의 차이.
