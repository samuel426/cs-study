# 프로세스와 스레드

- 날짜: 2026-10-05
- 분야: 운영체제 · Java
- 진행: 개념 설명과 확인 문제 5개
- 작성 방식: 학습 대화의 답변과 피드백을 바탕으로 정리

## 핵심 개념

- 프로그램은 실행할 명령이 담긴 파일이고, 프로세스는 실행 중인 프로그램의 인스턴스다.
- 서로 다른 프로세스의 메모리 공간은 기본적으로 분리되어 있다.
- 스레드는 프로세스 안의 실행 흐름이다. 같은 프로세스의 스레드들은 코드, 전역 데이터, 힙 등의 자원을 공유한다.
- 각 스레드는 자신만의 스택과 레지스터 상태를 가진다.
- 여러 스레드는 CPU에서 번갈아 실행될 수도 있고, 여러 코어에서 동시에 실행될 수도 있다.

## 확인 문제와 피드백

### 1. 두 스레드가 count를 한 번씩 증가시키면 항상 2인가?

**내 답변 요지:** 동기화가 없다면 2가 될 수도 있지만, 실행 상황에 따라 1이 될 수도 있다. Java의 동기화 키워드를 사용하면 다른 스레드가 기다리는 것으로 알고 있다.

**정리:** 맞다. 공유하는 일반 int 필드의 `count++`는 원자적인 연산이 아니다. 값을 읽고, 1을 더하고, 결과를 저장하는 과정이 겹칠 수 있다.

| 순서 | 스레드 A | 스레드 B | count |
|---|---|---|---|
| 1 | 0을 읽음 | | 0 |
| 2 | | 0을 읽음 | 0 |
| 3 | 읽은 값에 1을 더해 저장 | | 1 |
| 4 | | 읽은 값에 1을 더해 저장 | 1 |

이처럼 타이밍에 따라 결과가 달라지는 경쟁 상태가 발생하며, 위 예에서는 한 번의 증가가 유실된다.

### 2. 같은 데이터를 서로 다른 락으로 보호하면 안전한가?

**내 답변 요지:** 안전할 것 같지만, 함수 단계에서 객체를 가져오지 못해 오류가 날 것 같다.

**수정:** 서로 다른 락을 사용하면 두 스레드가 동시에 각 블록에 진입할 수 있어서 안전하지 않다. 락 객체들이 정상적으로 존재한다면, 락이 다르다는 이유만으로 오류가 발생하지는 않는다.

Java 키워드의 정확한 이름은 `synchronized`다. 데이터 자체에 접근 금지를 거는 것이 아니라, 같은 객체의 모니터 락을 사용하는 코드의 동시 진입을 제한한다. 락을 사용하지 않는 다른 접근까지 자동으로 막아주지는 않는다.

```java
class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }
}
```

인스턴스의 synchronized 메서드는 `this`의 락을 사용한다. 두 스레드가 같은 Counter 인스턴스의 이 메서드를 호출하면 서로 배제된다. 초기값이 0이고 다른 수정이 없다면 두 호출 완료 후 객체의 count는 2다. 결과를 다른 스레드에서 읽을 때도 join 또는 같은 락 사용 등 적절한 동기화가 필요하다.

### 3. 같은 프로세스의 스레드들은 왜 count를 함께 수정할 수 있는가?

**내 답변 요지:** count가 힙 메모리의 공유 객체에 있기 때문인 것 같다.

**정리:** 위 예제에서는 힙에 있는 Counter 객체의 인스턴스 필드가 count다. count 자체가 객체인 것은 아니다. 두 스레드가 같은 Counter 객체를 참조하기 때문에 동일한 필드를 수정할 수 있다.

### 4. 메서드의 기본형 지역 변수도 공유되는가?

```java
public void increment() {
    int amount = 1;
    count += amount;
}
```

**내 답변 요지:** A가 amount를 바꿔도 B에는 영향이 없을 것 같다. B가 실행할 때 함수가 새롭게 메모리를 차지하는 것 같다.

**정리:** 결론은 맞다. 함수 코드가 복제되는 것이 아니라, 각 호출의 스택 프레임이 해당 스레드의 스택에 생긴다. 기본형 지역 변수 amount는 호출마다 별도로 유지된다. 단, 공유 필드 count의 동시 수정 문제는 여전히 남는다.

### 5. 지역 참조 변수가 같은 객체를 가리키면 그 객체도 별개인가?

```java
public void update() {
    Counter local = sharedCounter;
    local.increment();
}
```

전제: 두 스레드의 sharedCounter가 동일한 객체를 참조한다.

**내 답변 요지:** 같은 객체의 값이 바뀔 것 같다.

**정리:** 맞다. local이라는 참조 변수는 각 호출에 따로 있지만, 참조 대상인 Counter 객체는 하나다. 따라서 수정하는 count도 하나다. 객체 공유 여부와 변경된 값이 다른 스레드에 언제 보이는지(가시성)는 구분해야 한다.

## 오늘 수정한 생각

- “synchronized는 자료 자체를 잠근다” → 같은 락을 획득해야 하는 코드끼리 동시 실행을 막는다.
- “서로 다른 락을 써도 안전하다” → 같은 공유 데이터를 보호하는 접근은 같은 락 등 일관된 동기화 방식을 사용해야 한다.
- “메서드를 실행하면 함수 코드가 새로 생긴다” → 호출마다 별도의 스택 프레임이 만들어진다.
- “지역 변수는 무조건 공유와 무관하다” → 지역 참조 변수들이 같은 힙 객체를 가리킬 수 있다.
