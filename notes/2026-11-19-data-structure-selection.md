# 자료구조 선택: 조회 비용, 저장량, 해시 충돌과 처리 순서

- 학습 기간: 2026-11-18~2026-11-19 (Asia/Seoul)
- 수업: CS-09 / 자료구조 · Java와 GC 복습
- 진행: 5/5문제 답변·피드백 완료. 문제 1~4는 18일, 문제 5는 19일 답변했다. 숙련 완료를 뜻하지 않는다.
- 목표: 조회 방식과 처리 순서에 맞는 자료구조를 고르고 시간 비용과 저장 공간을 구분하기.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| 시간과 공간 복잡도 | 조회가 평균 O(1)이어도 보관하는 항목이 늘면 저장 공간은 증가할 수 있음 |
| GC와 참조 | 살아 있는 일반 HashMap을 통해 강하게 도달 가능한 객체는 오래 조회하지 않았다는 이유만으로 회수되지 않음 |
| ArrayList | 내부 배열의 위치 번호로 접근. get(index)는 O(1). 위치 번호와 업무 ID는 다름 |
| LinkedList | 앞뒤 연결을 가진 노드를 따라 접근. 인덱스 조회는 가까운 끝부터 탐색하며 일반적으로 O(n) |
| HashMap | 키로 조회하며 해시가 적절히 분산되면 평균 O(1). 일반 HashMap은 삽입 순서를 보장하지 않음 |
| 해시 충돌 | 다른 키가 같은 버킷에 배정되는 상황. 실제 키를 구분하므로 같은 키의 값 갱신과 다름 |
| FIFO 큐 | 먼저 들어온 항목을 먼저 꺼내는 선입선출. ArrayDeque를 큐로 사용하면 offer로 뒤에 추가하고 poll로 앞에서 제거 |

## 확인 문제와 피드백

### 1. 빠른 조회와 메모리 사용량 · 11월 18일

**질문:** 한 스레드가 살아 있는 일반 HashMap<Long, Member>에 서로 다른 새 회원 ID와 새 Member 객체를 계속 추가한다. 삭제·만료·개수 제한은 없다. 조회가 평균 O(1)이므로 메모리도 일정하고 오래된 회원 객체는 GC가 회수한다는 주장에 동의하는가?

**사용자 첫 답변:** 회원 수가 늘어 해시가 적절히 분산되지 않으면 HashMap이 배열보다 메모리를 더 사용할 것 같다고 설명했다.

**피드백:** 같은 객체 참조를 보관하는 배열과 비교하면 맵의 내부 배열·엔트리 같은 관리 구조에 추가 공간이 필요할 수 있다. 그러나 해시가 잘 분산돼도 새 회원을 계속 저장하면 메모리는 증가한다. 해시 분산과 조회 비용, 보관하는 데이터 수와 저장 공간을 구분해야 한다. O(1)은 정확히 한 번의 연산이나 1초라는 뜻이 아니다.

**같은 문제의 재확인:** 맵에 남은 회원을 한 달간 조회하지 않았다면 GC가 오래됐다는 이유로 회수할 수 있는지 물었다. 사용자는 회수할 수 없으며 HashMap 안에 묶여 있기 때문이라고 답했다.

**보완:** 결론과 참조 보관의 방향은 맞다. 정확한 이유는 살아 있는 맵을 통해 객체에 도달할 수 있기 때문이다. 맵에서 제거해도 다른 강한 참조가 있으면 유지될 수 있고, 도달 불가능해져도 즉시 회수를 보장하지 않는다. 무제한 저장과 공간 증가의 설명은 독립적으로 검증하지 않았다.

### 2. 위치 번호로 반복 조회 · 11월 18일

**질문:** 한 스레드에서 데이터 10만 개를 한 번 담고 삽입·삭제는 거의 없이 get(50000), get(23000)처럼 여러 위치로 반복 조회한다. ArrayList와 LinkedList 중 무엇을 선택하며 이유는 무엇인가? 인덱스는 회원 ID가 아닌 위치 번호다.

**사용자 답변:** ArrayList는 인덱스 위치로 조회할 수 있고 LinkedList는 해당 위치까지 pointer를 따라가 시간이 더 걸리므로 ArrayList를 선택했다.

**피드백:** 선택과 이유가 정확하다. Java에서는 pointer를 보통 참조라고 표현한다. ArrayList의 get은 O(1), LinkedList의 일반적인 인덱스 조회는 O(n)이며 양 끝 접근은 O(1)이다. 원소 객체 자체가 배열 안에 연속 배치된다는 뜻은 아니다. 삽입·삭제 비용은 이번 답변으로 검증하지 않았다.

### 3. 같은 버킷과 같은 키 · 11월 18일

**질문:** 빈 HashMap에서 키 101과 201이 같은 버킷에 배정된다고 가정한다. 한 스레드가 put(101, "A"), put(201, "B"), put(101, "C")를 실행한 뒤 size(), get(101), get(201)의 값과 이유는?

**사용자 첫 답변:** 2, C, B라고 답했다. 같은 키면 재등록될 것 같지만 같은 버킷이라는 말은 잘 이해되지 않는다고 밝혔다.

**피드백:** 세 값이 모두 정확하다. 같은 키로 put하면 새 항목을 늘리는 것이 아니라 기존 값을 교체한다. 버킷은 항목들이 들어가는 후보 저장 구역이며 키 자체가 아니다. 설명용으로 버킷 번호를 키를 100으로 나눈 나머지로 정하면 101·201은 버킷 1, 102는 버킷 2다. 이 규칙은 실제 Java HashMap의 계산식이 아니다. 버킷 1에 (101, C), (201, B)를 함께 보관할 수 있으며 size는 버킷 수가 아닌 키-값 항목 수다.

**같은 문제의 재확인:** get(201)에서 버킷을 찾은 뒤 무엇을 확인해야 하는지 물었다. 사용자는 201을 가진 키를 찾아야 B를 반환할 수 있다고 답했다. 설명 후 같은 예제에서 실제 키 비교의 필요성을 확인했다. hashCode·equals 구현이나 새로운 충돌 사례는 검증하지 않았다.

### 4. 큐의 처리 순서 · 11월 18일

**질문:** 한 스레드가 아래 코드를 실행한다. first, second와 남은 큐의 앞→뒤 순서 및 이유는?

```java
Queue<String> q = new ArrayDeque<>();
q.offer("A");
q.offer("B");
q.offer("C");
String first = q.poll();
q.offer("D");
String second = q.poll();
```

**사용자 답변:** 각각 A, B이고 C, D가 순서로 남는다고 답했다.

**피드백:** 반환값과 남은 순서 모두 정확하다. D는 먼저 기다리던 B·C 뒤에 추가되어 FIFO를 유지한다. 이유는 보충 설명으로 제공했다. 모든 Java Queue 구현이 FIFO라고 일반화하지 않는다. LIFO는 마지막 항목을 먼저 꺼내는 후입선출이라고 소개했지만 별도 적용은 검증하지 않았다.

### 5. ID 조회와 도착 순서 처리 · 11월 19일

**질문:** 한 스레드에서 중복 없는 요청이 ID 875→120→640 순서로 도착한다. 대기 중인 요청을 ID로 빠르게 조회하면서 도착 순서대로 꺼내야 한다. ArrayList·HashMap·ArrayDeque 중 어떤 구조를 사용하거나 조합하며, 각각 무엇을 저장하고 어떤 역할을 맡기는가? 동시성·취소·재시도는 제외한다.

**사용자 답변:** 개수가 적고 도착 순서대로 처리해야 하므로 ArrayDeque가 좋을 것 같다고 답했다.

**피드백:** FIFO 요구를 위한 선택과 소량 데이터라는 판단은 타당하다. 문제에 규모나 조회 시간의 수치 조건이 없으므로 단일 큐를 무조건 오답으로 보지 않는다. 다만 ArrayDeque에 요청 객체를 보관하고 ID로 찾으려면 앞에서부터 비교해야 하며, 최악에는 n개를 확인하는 O(n) 탐색이다. 세 개 정도라면 실용적일 수 있지만 데이터가 늘어도 빠른 ID 조회를 원하면 다음 조합을 사용할 수 있다.

| 구조 | 저장 내용 | 역할 |
|---|---|---|
| HashMap<Long, Request> | 요청 ID → 요청 객체 | ID로 요청 내용 조회. 적절한 해시 분산에서 평균 O(1) |
| ArrayDeque<Long> | 875, 120, 640 순서의 요청 ID | 도착 순서 보관과 다음 처리 ID 꺼내기 |

요청 120의 내용은 map.get(120L)로 찾고, 처리할 때는 큐에서 875를 꺼낸 뒤 map.remove(875L)로 해당 요청 객체를 얻으면서 대기 목록에서 제거한다. 여기서는 큐에서 꺼낸 요청은 더 이상 대기 요청이 아니라고 정의한다. 요청 내용 전체를 두 번 복사할 필요는 없지만 큐의 ID와 맵의 관리 구조에 추가 공간이 필요하며 두 구조를 함께 갱신해야 한다.

**확인 범위:** 사용자 답변으로는 FIFO 선택과 소량일 때의 단순한 선택을 확인했다. 큐의 ID 탐색 비용, 두 구조의 역할 분담·제거·저장 비용은 보충 설명이며 독립적으로 검증하지 않았다.
