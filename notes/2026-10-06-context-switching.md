## 핵심 개념

컨텍스트 스위칭은 현재 실행 중인 스레드의 상태를 저장하고, 다음에 실행할 스레드의 상태를 복원하여 실행을 전환하는 과정이다. 여기서는 운영체제가 스케줄링하는 스레드를 기준으로 설명한다.

| 상태 | 필요한 이유 |
|---|---|
| 프로그램 카운터(PC) | 실행을 재개할 명령 위치를 알아야 한다. |
| 범용 레지스터 등 | 계산 중이던 값과 실행 상태를 되살려야 한다. |
| 스택 포인터(SP) | 해당 스레드의 스택 위치를 다시 사용해야 한다. |

스택 전체나 프로세스 메모리 전체를 매번 복사하는 것은 아니다. 기존 스택은 메모리에 남고, 필요한 CPU 상태를 저장·복원한다. 다른 프로세스에 속한 스레드로 전환할 때는 주소 공간을 전환하는 작업도 필요하다.

## 확인 문제와 피드백

### 1. 코어 하나에서도 음악을 들으며 문서를 작성할 수 있는가?

**내 답변 요지:** 문서를 입력할 때 스위칭해서 여러 작업이 동시에 돌아가는 것처럼 보일 것 같다.

**정리:** 번갈아 실행한다는 설명은 맞지만, 사용자 입력이 있을 때만 전환하는 것은 아니다. 실행 시간이 일정량 지나거나, 현재 스레드가 입출력 완료 등을 기다리며 실행을 멈추면 다른 실행 가능한 스레드로 전환할 수 있다.

키보드 입력으로 기다리던 스레드가 실행 가능한 상태가 되어도, 반드시 즉시 그 스레드로 전환되는 것은 아니다. 오디오 장치는 미리 준비된 데이터를 재생할 수 있으므로, CPU가 다른 일을 할 때마다 소리가 끊기는 것도 아니다.

- **동시성:** 여러 작업이 겹치는 기간 동안 진행된다. 코어 하나에서도 번갈아 실행하며 달성할 수 있다.
- **병렬성:** 여러 작업이 실제로 같은 순간에 실행된다.

### 2. 실행 위치만 복원하고 레지스터 값을 복원하지 않으면?

**내 답변 요지:** 엉뚱한 값으로 계산될 수 있을 것 같다.

**정리:** 맞다. A가 레지스터 값 10에 5를 더하려다 멈췄는데 B가 그 레지스터를 100으로 바꿨다면, A의 상태를 복원하지 않고 재개할 경우 잘못된 값을 사용하게 된다. 실행 위치와 계산 상태를 함께 보존해야 한다.

### 3. 전환 간격을 무조건 짧게 만들면 성능이 좋아지는가?

**내 답변 요지:** 어느 수준부터는 더 짧게 해도 사용자가 차이를 체감하지 못하고, 오히려 스위칭 비용 때문에 자원만 더 사용할 수 있다.

**정리:** 맞다. 더 자주 실행 기회를 주면 응답성이 좋아질 수 있지만, 상태 저장·복원과 스케줄링에도 CPU 시간이 든다. 이 추가 비용이 오버헤드다.

| 기준 | 의미 | 간격을 지나치게 줄였을 때 |
|---|---|---|
| 응답 시간 | 요청 후 반응하기까지의 시간 | 개선이 작아지거나 오버헤드로 악화될 수 있다. |
| 처리량 | 단위 시간에 완료한 작업의 양 | 실제 작업에 쓸 시간이 줄어 감소할 수 있다. |

적절한 간격은 작업 특성과 스케줄링 정책에 따라 다르다. 짧을수록 무조건 좋은 것은 아니다.

### 4. 같은 프로세스 안의 전환과 다른 프로세스 사이의 전환 중 어느 쪽이 더 비싼가?

**내 답변 요지:** 서로 다른 프로세스에 속한 스레드 사이의 전환이 더 비쌀 것 같다.

**정리:** 일반적으로 맞다. 두 경우 모두 스레드 실행 상태를 바꾸지만, 서로 다른 프로세스로 넘어가면 주소 공간도 바꿔야 한다. 같은 프로세스의 스레드들은 주소 공간을 공유한다.

전환에 따른 주소 변환 캐시의 영향은 [TLB 보충 자료](2026-10-06-tlb.md)에 정리했다. 실제 비용은 하드웨어, 운영체제, 캐시 상태 등에 따라 달라지므로 항상 일정한 비용 차이가 나는 것은 아니다.

### 5. 코어 하나에서 계산 작업을 스레드 100개로 나누면 더 빨라지는가?

전제: 해당 코어는 한 번에 스레드 하나만 실행하며, 작업은 파일·네트워크 대기가 거의 없는 계산 위주다. 같은 계산량을 비교한다.

**내 답변 요지:** 스레드 하나로 계산을 처리할 수 있을 것 같고, 여러 개로 나눠도 더 빨리 끝날 것 같지 않다.

**정리:** 결론은 맞다. 핵심은 작업이 작아서 스레드 하나로 충분하다는 것보다, 동시에 실행할 CPU 자원이 늘어나지 않는다는 점이다. 계산을 여러 스레드로 나누어도 번갈아 수행해야 하며, 전환·생성·관리 비용 때문에 더 느려질 수 있다.

여러 코어에서 나눠 실행할 수 있거나 입출력 대기 시간을 활용할 수 있는 경우는 조건이 다르다. 스레드 수만으로 성능 향상을 판단하면 안 된다.

## 오늘 보완한 생각

- “입력할 때만 스위칭한다” → 실행 시간 배분이나 대기 상태 진입 등으로도 전환할 수 있다.
- 실행 위치뿐 아니라 계산 중인 레지스터 상태도 복원해야 한다.
- 응답 시간과 처리량은 서로 다른 성능 기준이다.
- 다른 프로세스로 전환할 때 주소 공간이 바뀌지만, 메모리 전체를 복사하는 것은 아니다.
- 스레드 수가 늘어도 실제 병렬 실행 자원이 늘지 않으면 계산이 자동으로 빨라지지 않는다.
