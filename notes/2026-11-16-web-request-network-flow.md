# 웹 요청의 네트워크 흐름: DNS, TCP·UDP, TLS와 HTTP

- 날짜: 2026-11-16 (Asia/Seoul)
- 수업: CS-07 / 네트워크 · Java 복습
- 진행: 확인 문제 5/5개 답변·피드백 완료. 정답 5개나 숙련 완료를 의미하지 않는다.
- 목표: 주소 조회, 데이터 전달, 통신 보호, 요청·응답의 역할을 구분하고 흐름으로 설명하기.
- 예제는 학습용이며 실제 서비스 구현·측정 결과가 아니다.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| 호출별 스택 프레임 | 메서드를 호출할 때마다 매개변수·지역 변수 등을 위한 별도 작업 공간이 생김. 같은 객체를 사용해도 int 매개변수가 공유 필드가 되는 것은 아님 |
| DNS | 도메인 이름에 대응하는 IP 주소 등의 정보를 조회하는 시스템. 주소 조회 성공과 웹 서버 정상 동작은 별개 |
| TCP | 연결을 맺고 재전송과 순서 정리를 통해 신뢰성 있는 바이트 스트림 전달을 제공. 장애가 지속되면 실패할 수 있으며 자체 암호화 기능은 없음 |
| UDP | 데이터그램 단위로 전달하며 UDP 자체는 연결 수립, 손실 재전송, 순서 복구를 제공하지 않음. 필요한 기능은 상위 프로그램·프로토콜에서 구현 가능 |
| TLS | 암호화에 의한 기밀성, 변조 탐지에 의한 무결성, 통신 상대 인증을 제공. 일반적인 HTTPS에서는 서버 인증서를 검증 |
| HTTP | 요청과 응답의 의미·형식을 정하는 규칙. 서버는 요청에 대해 상태 코드와 필요한 내용 등을 응답 |
| HTTPS | TLS로 보호하는 HTTP 통신. 로그인 정보에만 선택적으로 적용되는 보호가 아님 |

매개변수의 저장 공간이 독립이라는 설명은 참조 대상 객체도 모두 독립이라는 뜻이 아니다. DNS 장애는 도메인 미등록뿐 아니라 레코드 누락, DNS 서버·통신 문제 등으로 발생할 수 있다. 도메인 등록과 DNS 설정의 역할은 다르며 제공 업체가 같을 필요는 없다.

## 확인 문제와 피드백

### 1. 같은 객체와 호출별 매개변수

**질문:** 두 요청이 같은 PriceService 객체를 사용한다. A가 total(2)를 호출하고 반환 직전에 멈춘 동안 B가 total(5)를 호출·반환한다. 이후 A가 재개한다. B와 A의 반환값 및 B가 A의 quantity를 바꾸는지와 이유는?

```java
class PriceService {
    public int total(int quantity) {
        return quantity * 1000;
    }
}
```

**사용자 첫 답변:** 둘 다 5000이다. 같은 객체를 사용하므로 B의 호출이 A의 quantity도 바꿀 것 같다.

**피드백:** 같은 객체 사용과 B의 5000은 맞다. A는 2000이다. quantity는 객체의 필드가 아니라 각 호출의 int 매개변수다. A의 프레임에는 2, B의 프레임에는 5가 따로 들어간다. B가 반환한 뒤에도 A는 자기 값을 사용한다. 메서드 코드를 공유하는 것과 호출별 값을 공유하는 것은 다르다.

**같은 문제 안의 재확인:** A의 값이 바뀌지 않는 이유를 다시 물었다. 사용자는 스택 프레임이라는 작업 공간이 생기기 때문이라고 답했다. “호출마다 별도의 프레임”이라는 표현을 강조했다. 설명 후 이유를 확인한 것이며 새로운 사례에서 독립적으로 정답을 낸 것으로 보지는 않는다.

### 2. DNS 조회 실패와 웹 접속

**질문:** 웹 서버는 정상인데 DNS 조회가 실패한다. 브라우저는 IP 주소를 모르고 저장 주소·기존 연결·대체 주소 확인 방법도 없다. 서버가 정상인데 접속할 수 없는 이유는?

**사용자 첫 답변:** DNS가 등록되지 않은 것 아니냐며 도메인 등록 업체에 등록해야 조회할 수 있을 것 같다고 말했다.

**피드백:** 등록 누락은 가능한 원인이지만 조회 실패만으로 확정할 수 없다. 도메인 등록은 이름을 사용할 권리를 등록하는 일, DNS 설정은 이름에 대응하는 IP 주소 등의 정보를 설정하는 일이다. 문제는 조회 실패의 원인을 확정하는 것이 아니라 접속이 막히는 직접 이유를 묻는다. 주어진 조건에서는 목적지 IP 주소를 얻지 못했기 때문에 접속하지 못한다.

**같은 문제 안의 재확인:** 사용자는 “브라우저가 목적지 IP 주소를 얻지 못해서 웹 서버가 정상이어도 접속 못한다”고 답했다. 조건에 맞는 인과관계를 확인했다. 실제 DNS 장애 원인 판별 능력은 검증하지 않았다.

### 3. 파일 전송에 적합한 방식

**질문:** 파일은 내용이 빠지거나 순서가 바뀌면 안 된다. 손실 재전송과 순서 복구를 직접 구현하지 않으려 할 때 TCP·UDP 중 무엇을 선택하고 왜 그런가?

**사용자 답변:** TCP를 선택한다. 재전송으로 복구가 가능하기 때문이다.

**피드백:** 선택과 재전송 이유가 정확하다. 원래 순서대로 데이터를 전달한다는 점까지 덧붙이면 요구 사항을 모두 설명할 수 있다. UDP 자체에는 재전송·순서 복구 기능이 없지만 이를 상위에서 구현할 수 있다. TCP도 연결 장애가 지속되면 전송에 실패할 수 있다.

**확인 범위:** TCP 선택과 재전송 이유를 답변으로 확인했다. 순서 보장, TCP 실패 가능성, UDP 위의 별도 구현은 설명만 했으며 독립적인 적용 답변은 없다.

### 4. TCP만으로 로그인 정보를 보호할 수 있는가

**질문:** “TCP는 신뢰성 있게 전달하므로 TCP 연결만 성공하면 비밀번호도 안전하게 보낼 수 있고 TLS는 필요 없다”는 주장에 동의하는가? 두 기술의 역할 차이로 설명하기.

**사용자 답변:** TCP는 전송 방식에 관한 것이고 TLS로 암호화나 증명서가 동반되어야 제대로 된 전송으로 볼 수 있을 것 같다.

**피드백:** 신뢰성 있는 전달과 통신 보안을 구분한 방향이 맞다. TCP만으로도 정상 전송은 가능하므로 “제대로 된 전송”을 “통신 내용을 보호하고 서버 신원을 확인하는 전송”으로 구체화했다. 일반적인 HTTPS에서 사용하는 용어는 인증서이며 서버 신원 확인에 사용한다. TLS는 변조 탐지도 제공한다.

**확인 범위:** 전송과 보안의 구분, TLS의 암호화·인증서 필요성을 답했다. 변조 탐지와 인증서 검증 세부 원리는 독립적으로 확인하지 않았다.

### 5. HTTPS 새 접속의 전체 흐름

**질문:** 저장된 IP 주소·기존 연결·TLS 세션 재개 없이 HTTP/1.1 기반 HTTPS 사이트에 새로 접속한다. A=HTTP 요청과 응답, B=TLS 보안 통신 준비, C=DNS 조회, D=TCP 연결을 순서대로 나열하고 각 역할을 한 문장씩 설명하기.

**사용자 답변:** C → D → A → B. DNS 조회로 목적지를 정하고 TCP 연결을 보낸다. HTTP로 기본 요청과 응답을 하며 로그인처럼 암호화할 정보는 TLS로 작업한다.

**피드백:** DNS 다음 TCP라는 앞부분과 HTTP의 요청·응답 역할은 맞다. HTTPS의 새 연결에서는 HTTP 요청을 보내기 전에 TLS로 보안 통신을 준비하므로 정답은 C → D → B → A다. DNS는 목적지를 임의로 정하는 것이 아니라 접속할 이름에 대응하는 주소를 조회한다. TCP는 연결을 맺는다고 표현한다.

| 순서 | 역할 |
|---|---|
| C · DNS | 접속하려는 도메인 이름에 대응하는 IP 주소 조회 |
| D · TCP | 그 주소의 서버와 신뢰성 있는 데이터 전달을 위한 연결 수립 |
| B · TLS | 서버 신원 확인과 암호화 등 보안 통신 준비 |
| A · HTTP | 보호된 연결로 요청을 보내고 서버의 응답을 받음 |

TLS는 로그인할 때만 추가하는 기능이 아니다. 해당 HTTPS 연결의 일반 페이지 요청·응답도 보호한다. HTTP 요청을 평문으로 먼저 보낸 뒤 나중에 TLS를 적용해도 이미 보낸 내용을 소급해서 보호할 수는 없다. HTTPS에서도 요청·응답 규칙은 HTTP이며 그 통신을 TLS로 보호한다.

**확인 범위:** 마지막 순서와 TLS 적용 범위는 오답을 피드백으로 보완한 상태다. 사용자가 수정된 흐름을 다시 설명하지 않았으므로 이해 검증 완료로 표시하지 않는다. 추가 6번 문제는 내지 않고 다음 수업의 기본 5문제 안에 복습한다.

## 답변으로 확인한 내용과 다음 복습

- 설명 후 호출별 스택 프레임이 A의 매개변수를 유지하는 이유임을 답했다. 새 사례 적용은 계속 복습한다.
- 설명 후 DNS 조회 실패와 목적지 IP 부재, 접속 실패의 관계를 답했다.
- 파일 전송에서 TCP를 선택하고 재전송을 이유로 들었다. 순서 보장까지 포함하는 답변을 복습한다.
- TCP 전송과 TLS 암호화·인증서의 역할을 구분했다. 무결성·인증서 검증 세부 사항은 미검증이다.
- 우선 복습: HTTPS에서 TLS가 HTTP 요청보다 먼저 준비되는 이유와 로그인 외의 요청·응답도 보호한다는 점.
- TCP 연결 수립 메시지, 흐름·혼잡 제어, DNS 계층별 조회, IP·포트·라우팅, HTTP 메서드·상태 코드 전반, TLS 암호화·키 합의의 세부 알고리즘은 미진행이다.
- 이번 순서는 HTTP/1.1 기반의 새 HTTPS 연결이라는 조건에 한정한다. 연결 재사용·세션 재개·다른 HTTP 버전의 흐름을 모두 동일하다고 일반화하지 않는다.
