# 인증과 API 보안: 접근 권한, 세션, JWT, 입력 검증과 로그

- 학습일: 2026-11-19 (Asia/Seoul)
- 수업: CS-10 / 웹 보안 · HTTPS 복습
- 진행: 복습 포함 5/5문제 답변·피드백 완료. 수업 완료이며 숙련 완료를 뜻하지 않는다.
- 목표: 인증과 인가를 구분하고 서버가 검증해야 할 값과 로그에서 제외해야 할 비밀정보를 설명하기.
- 같은 날 앞서 자료구조의 마지막 1문제를 마쳤으므로 이날 실제 답변은 총 6개다. 용어 보충 설명은 추가 문제로 세지 않는다.

## 핵심 개념

| 개념 | 역할과 한계 |
|---|---|
| 인증 | 요청자가 누구인지 확인. 로그인 상태만으로 모든 데이터 접근이 허용되지는 않음 |
| 인가 | 해당 사용자가 요청한 데이터나 기능에 접근할 권한이 있는지 검사 |
| HTTPS | 전송을 보호하지만 서버의 데이터 접근 권한 판단을 대신하지 않음 |
| 서버 세션 | 서버가 관리하는 로그인 상태. 서버 측 유효성·만료 검사 필요 |
| 세션 ID | 서버의 세션을 찾는 식별값. 유효한 값이 노출되면 사칭에 악용될 수 있음 |
| 쿠키 | 브라우저가 값을 저장하고 조건에 맞는 요청에 보내는 수단. 쿠키 보관 기간과 서버 세션 유효 기간은 별개 |
| 토큰과 JWT | 토큰은 인증·접근 등에 쓰는 증표이며 JWT는 정보를 담는 토큰 형식. 모든 토큰이 JWT인 것은 아님 |
| JWT 서명 검증 | 신뢰하는 키로 요청의 내용과 서명을 검증. 서명만으로 내용을 숨기지는 않으며 만료·발급자·대상 등도 검사 |
| 입력 검증 | 받은 값의 형식·범위가 규칙에 맞는지 검사. 브라우저 검사와 별도로 서버에서 변경 전에 수행 |
| 로그 | 추적에 필요한 시각·요청 식별자·결과 등을 기록하되 비밀번호·세션 ID·접근 토큰 원문은 제외 |

## 확인 문제와 피드백

### 1. 로그인과 다른 회원 주문 조회

**질문:** 주문은 소유자 본인만 조회할 수 있다. 회원 A가 정상 로그인한 상태에서 HTTPS로 자기 주문 /orders/100을 요청하다 주소를 B의 주문 /orders/200으로 바꿨다. 서버는 로그인 여부만 확인하고 B의 주문을 반환한다. 허용해도 되는가? 추가로 무엇을 검사하며 HTTPS만으로 해결되지 않는 이유는?

**사용자 답변:** 보여 주면 안 되지만 지금 구현에서는 보일 것 같다고 판단했다. 인가가 제대로 설정되지 않았으며 서버가 해당 데이터의 조회 권한을 확인해야 한다고 설명했다. 쿠키로 하는 것인지 물었고 놀이동산 티켓처럼 유효 시간이 있는 무언가를 기억하지만 용어는 모르겠다고 밝혔다.

**피드백:** 허용해야 하는 동작과 현재 동작을 구분했고 인가 누락도 정확히 짚었다. 서버가 검증한 로그인 사용자 A와 서버에 저장된 주문 200의 실제 소유자 B를 비교하여 거부해야 한다. HTTPS는 전송을 보호하지만 서버가 잘못된 대상에게 데이터를 반환하는 것까지 막아 주지는 않는다. 소유자 비교의 구체적 기준과 HTTPS의 한계는 보충 설명이며 독립적으로 검증한 내용은 아니다.

**용어 보충:** 전형적인 서버 세션 방식에서 세션은 서버의 로그인 상태, 세션 ID는 이를 찾는 번호, 쿠키는 브라우저가 값을 보관·전달하는 수단이다. 로그인 성공 후 서버가 추측하기 어려운 ID와 사용자·만료 시각을 연결하고 브라우저에 그 ID를 담은 쿠키를 설정한다. 이후 요청의 세션 유효성과 데이터 접근 권한은 서버가 검사한다. 토큰은 증표를 뜻하며 세션 ID도 세션 토큰이라고 부를 수 있다. 쿠키·세션·토큰을 같은 층위의 서로 배타적인 세 선택지로 외우지 않는다.

### 2. 쿠키가 남아 있는 만료 세션

**질문:** 서버 세션은 S7→회원 A, 만료 14:30이다. 브라우저는 S7 쿠키를 내일까지 보관한다. 현재 14:31에 로그인 필수인 내 주문 조회를 요청한다. 다른 인증 수단이나 자동 갱신은 없다. 쿠키가 남아 있다는 이유로 로그인 상태를 인정해도 되는가? 서버는 무엇을 기준으로 판단하는가? S7은 설명용 축약이며 실제 보안용 세션 ID가 아니다.

**사용자 답변:** 인정하면 안 되며 만료 시각을 기준으로 판단해야 한다.

**피드백:** 거부 판단과 만료 기준이 정확하다. 정확히는 서버가 관리하는 세션의 만료 시각을 기준으로 한다. 쿠키가 브라우저에 남아 있어도 서버 세션이 만료됐다면 로그인 상태로 인정할 수 없다. 사용자 답변에서 서버 측 기준을 별도로 명시한 것으로 기록하지 않는다.

### 3. JWT 내용 변경과 서명 검증

**사전 설명:** JWT(JSON Web Token)는 사용자 식별자·만료 시각 같은 정보를 담을 수 있는 토큰 형식이다. 이번 예제는 암호화 없이 서명한 JWT다. 내용은 읽을 수 있고 서명은 내용의 변경 여부와 신뢰하는 발급자의 서명인지 검증하는 데 사용한다. 암호화는 내용을 숨기는 역할이다. 서버는 서명 외에도 만료 시각·발급자·사용 대상 등을 확인해야 한다.

**질문:** 신뢰하는 서버가 userId=A, role=USER, 만료 15:00인 JWT를 발급하고 서명했다. 14:00에 A가 role을 ADMIN으로 바꾸고 기존 서명은 그대로 보냈다. A는 발급자의 서명 키를 모르고 서버는 올바른 키·알고리즘으로 검증한다. 만료 전이므로 관리자 요청을 허용해도 되는가? 무엇을 검사해 변경을 알아내는가? 표기는 실제 토큰 문자열을 읽기 쉽게 풀어 쓴 것이다.

**사용자 답변:** 허용하면 안 된다. 서버가 처음 받은 서명을 기준으로 내용을 검사했을 때 바뀌었으면 막아야 한다.

**피드백:** 거부 판단과 서명 검증의 방향은 정확하다. 다만 처음 발급한 원본 토큰을 따로 저장하고 비교하는 것이 필수라는 뜻은 아니다. 요청으로 받은 서명 대상 내용과 서명을 서버가 신뢰하는 검증 키·알고리즘으로 검증한다. 원래 내용과 서명은 검증에 성공하지만 바뀐 내용과 원래 서명의 조합은 실패한다. 서명으로 원래 내용을 복원하는 것은 아니다. 검증 키와 원본 보관 여부의 정확한 설명은 보충이며 독립적으로 확인하지 않았다.

### 4. 브라우저 검사와 서버 입력 검증

**질문:** 주문 수량 규칙은 1~10의 정수다. 브라우저 화면만 범위를 검사하고 서버에는 수량 검사 코드가 없다. 로그인·주문 권한 검사에 정상 통과한 사용자가 화면을 거치지 않고 quantity=-3을 직접 요청한다. 아래 실행 결과와 문제점, 브라우저 검사만으로 부족한 이유와 필요한 검사 위치는? 동시 요청·다른 변경은 없다.

```java
int stock = 10;
int quantity = -3; // 요청으로 받은 수량
stock = stock - quantity;
```

**사용자 답변:** 최종 재고는 13이다. 음수 수량에는 서버가 잘못된 수량이라고 회신해야 하는데 그렇지 않다. stock 갱신 전에 quantity 검증 로직을 추가해야 한다.

**피드백:** 계산, 오류 응답, 서버에서 변경 전 검증해야 한다는 위치가 정확하다. 규칙 전체는 1~10의 정수이므로 음수뿐 아니라 0·11·소수도 거부해야 한다. 올바르게 거부하면 재고는 10으로 유지된다. 브라우저 검사는 빠른 피드백에 도움이 되지만 화면을 거치지 않은 요청이 가능하므로 서버가 직접 검증해야 한다. 형식·전체 범위와 브라우저 우회 이유는 보충 설명이다. 모든 입력 검증을 단순 범위 검사만으로 해결할 수 있다고 일반화하지 않는다.

### 5. 장애 로그와 인증 비밀정보

**사전 설명:** 로그는 처리 결과나 오류를 남기는 기록이다. requestId는 한 요청의 여러 로그를 연결하는 추적 번호이며 이 예제에서는 로그인 수단이 아니다.

**질문:** 주문 API 장애 분석을 위해 모든 요청 정보를 로그에 기록하자는 제안이 있다. 후보는 처리 시각, requestId, API 경로 /orders, 오류 코드 INVALID_QUANTITY, 비밀번호 원문, 아직 유효한 세션 ID 또는 접근 토큰 원문이다. 무엇을 남기고 제외할지, 특히 유효한 로그인 증표가 노출될 때의 위험을 설명하기. 실제 비밀값은 제시하지 않았다.

**사용자 답변:** 비밀번호 원문과 로그인 증표는 넣으면 안 될 것 같다. 그 사람이 아닌데도 데이터에 접근할 수 있는 문제가 생긴다.

**피드백:** 제외 대상과 사칭·무단 접근 위험을 정확히 설명했다. 보유만으로 사용할 수 있는 일반적인 세션 ID나 Bearer 접근 토큰은 노출된 값을 재사용해 사용자를 사칭하는 데 악용될 수 있다. 여기서 Bearer는 증표를 가진 사람이 제시하여 사용하는 방식을 뜻한다. 만료·폐기·추가 검증 등에 따라 실제 사용 가능 여부는 달라지므로 모든 토큰이 언제나 재사용된다고 일반화하지 않는다.

**보충:** 이번 예제의 처리 시각·requestId·API 경로·오류 코드는 문제 추적에 필요한 기록으로 남길 수 있다. 비밀번호·로그인 증표 원문을 제외하고 필요한 필드만 선택한다. requestId는 세션 ID와 역할이 다르다. 사용자가 남길 네 항목을 각각 나열한 것은 아니므로 이 분류는 보충 설명으로 기록한다.
