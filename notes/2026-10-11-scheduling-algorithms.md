## 핵심 개념

한 코어에서 한 번에 작업 하나만 실행한다고 가정했다. 계산 예제는 입출력 대기·자발적 양보가 없고, 작업이 도착하면 준비 상태가 된다. 문제 1·2·4의 전환 비용은 계산을 위해 0으로 두었으며, 문제 5에서는 실제로 전환 비용이 든다는 점을 고려했다.

| 방식 | 선택 기준 | 오늘 확인한 특징 |
|---|---|---|
| FCFS(First Come, First Served) | 준비 큐에 먼저 들어온 작업부터 | 비선점 방식. 긴 작업 뒤의 짧은 작업도 기다릴 수 있음 |
| SJF(Shortest Job First) | 준비된 작업 중 다음 CPU 실행 구간이 짧은 작업부터 | 오늘은 필요한 시간을 알고 있는 비선점 예제. 짧은 작업이 계속 준비되면 긴 작업에 기아가 생길 수 있음 |
| 라운드 로빈(Round Robin) | 준비 큐 순서로 한 번에 최대 타임 슬라이스만큼 실행 | 미완료 작업은 선점해 큐 맨 뒤로 보내고, 완료한 작업은 큐에서 빠짐 |

이번 스케줄링 계산에서 **응답 시간 = 첫 CPU 실행 시각 − 도착 시각**이다. 실제 앱의 첫 화면 반응 시점과 첫 CPU 실행 시점이 항상 같다는 뜻은 아니다. **도착부터 완료까지 걸린 시간 = 완료 시각 − 도착 시각**이며, 작업 자체에 필요한 CPU 실행 시간과도 구분한다.

## 확인 문제와 피드백

### 1. FCFS에서 B의 첫 실행과 완료는 언제인가?

**질문:** A는 0ms에 도착해 CPU 8ms가 필요하고, B는 1ms에 도착해 CPU 1ms가 필요하다. FCFS에서 B는 몇 ms에 처음 실행될까? B의 도착부터 첫 실행까지, 도착부터 완료까지는 각각 몇 ms일까? 이유도 설명해 줘.

**내 답변:** “8ms에 처음 실행 도착은 1ms 완료는 9ms”

**피드백:** 세 시각 모두 맞다. A가 0~8ms, B가 8~9ms 실행한다. 요청한 경과 시간과 이유는 직접 답하지 않아 보완했다.

- B의 응답 시간: 8 − 1 = **7ms**
- B의 도착부터 완료까지: 9 − 1 = **8ms**

시각과 걸린 시간의 차이는 피드백으로 설명했다. 도착 시각이 0이 아닌 예제의 계산을 사용자가 직접 확인한 것으로 기록하지 않는다.

### 2. SJF의 실행 순서와 B의 응답 시간은?

**질문:** A·B·C가 모두 0ms에 준비되고 필요한 CPU 시간은 각각 8ms·4ms·1ms다. FCFS의 동시 도착 처리 순서는 A→B→C로 정한다. 비선점 SJF에서는 어떤 순서로 실행할까? B의 첫 실행까지 기다리는 시간은 FCFS와 SJF에서 각각 얼마일까? 순서를 고른 이유도 설명해 줘.

**내 답변:** “c b a 순서로 진행되고 b의 응답 시간은 3ms야”

**피드백:** C→B→A 순서는 맞다. CPU 실행 길이 1ms·4ms·8ms 순으로 고른다. SJF에서는 C가 0~1ms, B가 1~5ms, A가 5~13ms 실행한다.

| 방식 | B의 첫 실행 시각 | B의 응답 시간 |
|---|---:|---:|
| FCFS | 8ms | 8 − 0 = 8ms |
| SJF | 1ms | 1 − 0 = 1ms |

3ms라는 답은 수정했다. 계산 근거는 답변에 없어 추정하지 않는다. FCFS의 응답 시간과 선택 이유는 직접 답하지 않아 피드백으로 보완했다. B 자체의 CPU 실행 시간 4ms와 첫 실행까지 기다린 시간 1ms는 다르다.

### 3. 짧은 작업이 계속 들어오는 SJF에서 긴 작업은 반드시 실행되는가?

**질문:** CPU 20ms가 필요한 L이 준비 상태로 기다린다. 비선점 SJF에서 다음 작업을 고를 때마다 CPU 1ms가 필요한 새 작업이 적어도 하나 준비되어 있다. 이 상황이 계속되면 L은 언젠가 반드시 실행될까? 이유와 함께, L도 실행 기회를 얻도록 선택 기준에 무엇을 추가하면 좋을지 설명해 줘.

**내 답변:** “반드시 실행안될거 같은데, 기아? 알고리즘? 비슷한거 굶주리는 상황 생각난다”

**피드백:** 실행 보장이 없다는 취지와 기아를 떠올린 것은 맞다. **기아(starvation)**는 알고리즘 이름이 아니라, 실행 가능한 작업이 계속 선택에서 밀려 CPU를 받지 못하는 현상이다. 매번 더 짧은 작업이 있으므로 L은 계속 밀릴 수 있다.

**보충 설명:** 해결 아이디어는 직접 답하지 않아 설명했다. CPU 배정을 기다린 시간을 고려하고, 오래 기다린 작업의 우선순위를 높이는 **에이징(aging)**을 적용할 수 있다. 이는 실행 길이만 보는 순수 SJF에 다른 선택 기준을 더하는 것이다. 에이징의 이해는 아직 사용자 답변으로 확인되지 않았다. 관련 자료는 [이전 수업의 참고 자료](2026-10-07-cpu-scheduling-basics.md#참고-자료)에 있다.

### 4. 라운드 로빈에서 B가 먼저 실행 기회를 얻는 이유는?

**질문:** A·B가 모두 0ms에 도착하고 CPU 시간은 A 5ms·B 3ms다. 초기 준비 큐는 A→B, 타임 슬라이스는 2ms다. 0~2ms와 2~4ms에는 각각 누가 실행되고, B의 응답 시간은 몇 ms일까? 같은 순서의 FCFS보다 B가 일찍 실행될 수 있는 이유도 설명해 줘.

**내 답변 요지:** 0~2ms는 A, 2~4ms는 B이고 B의 응답 시간은 2ms다. 라운드 로빈은 타임 슬라이스에 따라 순환하며 실행 대상이 바뀌기 때문이다.

**피드백:** 실행 대상, 응답 시간 2 − 0 = 2ms와 이유 모두 맞다. A가 아직 끝나지 않았어도 2ms를 쓰면 선점되어 B에게 기회가 온다. FCFS에서는 A가 완료하는 5ms까지 B가 기다린다는 비교를 보충했다.

문제 2에서는 응답 시간을 잘못 계산했지만, 이번 0ms 도착 예제에서는 정확하게 답했다. 도착 시각이 0이 아닌 예제까지 숙련했다고 확대하지 않는다.

### 5. 타임 슬라이스가 너무 짧거나 길면 어떤 문제가 생기는가?

**질문:** 한 코어에서 한 번에 작업 하나를 실행하며 CPU를 오래 사용하는 작업 여러 개가 계속 준비되어 있다. 라운드 로빈을 사용하고 전환 비용은 0이 아니다. 타임 슬라이스가 너무 짧을 때와 너무 길 때 각각 어떤 단점이 생길까? 적절한 길이를 정하려면 무엇과 무엇 사이의 균형을 고려해야 할까?

**내 답변 요지:** 너무 짧으면 스위칭 비용이 커지고, 너무 길면 긴 작업 때문에 짧은 작업의 응답 시간도 늘어날 수 있다. 작업의 실행 시간 크기를 보며 타임 슬라이스를 적절히 조절해야 할 것 같다.

**피드백:** 두 단점 모두 맞다. 정확히는 타임 슬라이스가 짧아지면 **전환 횟수가 늘어 전체 전환 비용과 그 비중이 커질 수 있다**. 전환 한 번의 비용이 반드시 커진다는 뜻은 아니다. 길어지면 현재 작업이 CPU를 더 오래 사용하므로 뒤에 있는 작업이 첫 실행까지 오래 기다릴 수 있다.

작업의 CPU 실행 길이를 살피자는 생각도 타당하다. 여기에 원하는 응답 속도, 전환 비용, 준비된 작업 수 등을 함께 고려해야 한다. 핵심은 **응답성과 전환 오버헤드(실제 작업 외에 드는 추가 비용)의 균형**이다. 실행 시간만으로 타임 슬라이스가 자동 결정되거나 무조건 짧을수록 좋은 것은 아니다.

## 오늘 보완한 생각과 복습 포인트

- 첫 실행·완료의 **시각**과 도착부터 걸린 **시간**을 구분한다.
- SJF 순서는 맞혔지만 응답 시간 계산을 수정했다. 이후 라운드 로빈의 0ms 도착 예제에서는 응답 시간을 정확히 계산했다.
- 기아는 현상, 에이징은 그 현상에 대응하는 방법이다. 에이징은 설명으로 보완했으며 별도 답변으로 검증하지 않았다.
- 라운드 로빈은 앞 작업의 완료를 기다리지 않고 뒤 작업에 기회를 줄 수 있다는 이유를 답변으로 확인했다.
- 타임 슬라이스가 짧거나 긴 경우의 단점은 답변으로 확인했다. 전환 한 번의 비용과 누적 비용의 차이는 피드백으로 정밀하게 보완했다.
