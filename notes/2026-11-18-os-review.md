# 운영체제 복습: 공유 범위, 동기화, 교착 상태와 주소 변환

- 수업: CS-08 / 운영체제 · HTTPS 복습
- 진행: 5/5문제 답변·피드백 완료. 문제 1은 17일, 문제 2~5는 18일 답변했다. 이틀에 걸친 한 수업이며 숙련 완료를 뜻하지 않는다.
- 목표: 자원의 공유 범위와 보호 범위, 락의 보유·대기 관계, 프로세스별 주소 변환을 설명하기.
- 문제 5의 용어 설명과 이유 재확인은 같은 문제 안의 보충이며 추가 문제로 세지 않는다.

## 핵심 개념

| 개념 | 설명 |
|---|---|
| HTTPS 복습 | 공개 페이지라도 HTTPS 접속에서는 TLS 준비 후 HTTP 요청을 보냄. HTTP/1.1의 새 연결이며 연결·세션 재사용이 없는 사례 |
| 프로세스와 스레드 | 프로세스는 보통 별도 주소 공간을 가지며 같은 프로세스의 스레드는 자원을 공유할 수 있음. 별도 프로세스도 통신·공유 메모리 등의 명시적 수단으로 공유 가능 |
| Java 객체와 호출별 변수 | 같은 JVM의 스레드는 힙의 같은 객체를 함께 사용할 수 있지만 스택과 호출별 변수는 구분됨 |
| 동기화 범위 | 같은 값에 의존하는 읽기·계산·저장을 하나의 작업으로 보호해야 갱신 유실을 막을 수 있음 |
| 교착 상태 | 서로가 가진 자원을 기다려 진행하지 못하는 상태. 대기 자체와 교착은 다름 |
| 페이지·프레임 | 페이지는 가상 주소 공간의 구간, 프레임은 같은 크기의 물리 메모리 구간 |
| 페이지 테이블 | 가상 페이지 번호와 물리 프레임 번호를 대응시키는 표 |
| 오프셋 | 구간 시작점으로부터의 바이트 거리. 주소 변환에서 페이지 번호를 프레임 번호로 바꿔도 오프셋은 유지 |

## 확인 문제와 피드백

### 1. 공개 페이지의 TLS 준비 · 11월 17일

**질문:** 로그인 없이 읽는 공개 공지사항을 HTTP/1.1 기반 HTTPS로 처음 요청한다. DNS 조회와 TCP 연결은 완료됐고 기존 연결·TLS 세션 재사용은 없다. A=HTTP 요청과 B=TLS 준비 중 무엇이 먼저이며 로그인 여부가 선택에 영향을 주는가?

**사용자 답변:** B를 선택했다. 정보가 조회되는 것이므로 보안이 필요해 보인다고 설명했다.

**피드백:** 공개 페이지에서도 TLS가 먼저라는 선택은 정확하다. 직접 근거는 HTTPS라는 조건이며 정보가 민감한지에 따라 TLS를 켜고 끄는 것이 아니다. 공개 공지도 서버 신원과 전송 중 변조 여부를 확인할 가치가 있다. 이 이유는 보충 설명이며 사용자가 HTTPS 조건을 근거로 독립적으로 답한 것으로 보지는 않는다.

### 2. 프로세스·스레드의 객체 공유 · 11월 18일

**질문:** A는 한 Java 프로세스의 두 스레드가 같은 Counter 객체의 count를 증가시킨다. B는 두 Java 프로세스가 각각 new Counter()로 별도 객체를 만들어 증가시킨다. B에는 프로세스 간 통신·공유 메모리가 없다. 같은 count 저장 공간에 두 실행 흐름의 수정이 겹칠 수 있는 쪽과 이유는?

**사용자 답변:** A다. 두 스레드가 같은 Counter 객체에 접근하기 때문이다.

**피드백:** 선택과 이유가 정확하다. A는 같은 객체의 필드를 공유하고 B는 각각 별도 객체를 가진다. 같은 클래스·필드 이름만으로 저장 공간이 같아지는 것은 아니다. 모든 프로세스 간 경쟁이 불가능하다고 일반화하지 않는다.

### 3. 쓰기만 잠근 증가 연산 · 11월 18일

**질문:** 초기 count=0인 같은 Counter에서 두 스레드가 각각 한 번 아래 메서드를 호출한다. T1이 0을 읽어 next=1, T2도 0을 읽어 next=1을 계산한다. 이후 T1이 락 안에서 저장·해제하고 T2가 저장·해제한다. 최종값과 필요한 보호 범위는? 다른 변경은 없고 두 호출 완료 후의 값을 묻는다.

```java
private int count = 0;
private final Object lock = new Object();

public void increment() {
    int next = count + 1;
    synchronized (lock) {
        count = next;
    }
}
```

**사용자 답변:** count=1이고 `int next = count + 1;`을 synchronized 안에 넣어야 한다.

**피드백:** 결과와 수정 범위 모두 정확하다. 각 호출의 next가 따로 있어도 같은 이전 값으로 계산했으므로 1을 차례로 저장한다. 아래처럼 읽기·계산·저장을 같은 락으로 묶으면 다음 호출은 이전 호출이 저장한 1을 읽어 2를 저장한다. 상세 실행 설명은 피드백으로 제공했다.

```java
public void increment() {
    synchronized (lock) {
        int next = count + 1;
        count = next;
    }
}
```

### 4. 락 획득 순서와 교착 여부 · 11월 18일

**질문:** L1·L2가 처음에는 비어 있고 두 스레드 모두 L1을 얻어 유지한 채 L2를 얻고 유한한 작업 후 해제한다. A가 L1을 획득하고 B가 L1에서 기다린 뒤 A가 L2를 얻으려 한다. 다른 스레드·락은 없다. 교착 상태인지, B가 가진 락과 기다리는 락, A의 진행 가능성을 근거로 설명하기.

**사용자 답변:** 교착은 아니다. B가 L2를 가져가 A가 L2를 기다리는 상황이면 교착이지만 지금은 그렇지 않으며 A가 끝나면 B가 가져가 진행할 것 같다.

**피드백:** 판단과 서로 상대의 락을 기다리는 상황과의 비교는 정확하다. 현재 B는 가진 락 없이 L1을 기다리고 A는 비어 있는 L2를 얻을 수 있다고 구체화했다. A 스레드 전체 종료는 필요 없고 작업 후 L1을 해제하면 B가 획득할 수 있다. B의 정확한 보유·대기 상태와 종료·해제 구분은 피드백으로 보완한 내용이다.

### 5. 가상 주소와 물리 주소 계산 · 11월 18일

**질문:** 교육용으로 페이지·프레임 크기는 16바이트, 주소·번호는 0부터 시작한다. P·Q가 각각 가상 주소 20에 접근한다. P의 페이지 1은 프레임 3, Q의 페이지 1은 프레임 7에 대응한다. 모두 RAM에 있고 접근 가능하다. 각각의 물리 주소와 결과가 같거나 달라지는 이유는? 물리 주소=프레임 번호×16+오프셋 공식을 제시했다.

**사용자 첫 답변:** P=18, Q=22일 것 같다. 프레임의 정확한 역할은 모르지만 프레임 대응 때문에 같은 가상 주소라도 결과가 달라질 수 있을 것 같다고 설명했다. 계산 과정을 밝히지 않았으므로 오답 산출 방식을 추측하지 않는다.

**피드백:** 프로세스별 대응 때문에 물리 위치가 달라질 수 있다는 방향은 맞다. 정답은 P=52, Q=116이다. 프레임 번호는 바이트 주소가 아니라 구간 번호다.

| 항목 | 이번 예제 |
|---|---|
| 가상 주소 | 프로그램이 사용하는 주소 20 |
| 가상 페이지 번호 | 20÷16의 몫인 1 |
| 페이지 시작 주소 | 1×16=16 |
| 오프셋 | 20−16=4. 시작점에서 4바이트 떨어진 위치 |
| P의 프레임 번호 | P의 페이지 테이블에서 페이지 1에 대응하는 3 |
| P의 프레임 시작 주소 | 3×16=48 |
| P의 물리 주소 | 48+4=52 |
| Q의 물리 주소 | 7×16+4=116 |

**첫 재확인:** 48에 더하는 4의 의미와 출처를 물었다. 사용자는 4가 오프셋이라고 답했지만 헷갈린다며 용어 정리를 요청했다. 이 시점에는 용어 이름만 확인했다.

**추가 설명:** 주소는 바이트 위치, 페이지·프레임은 일정 크기 구간, 번호는 구간에 붙인 번호, 오프셋은 구간 안의 거리, 페이지 테이블은 대응표로 구분했다. 프레임 3은 48~63, 프레임 7은 112~127이다. 가상 주소 20을 페이지 1·오프셋 4로 나누고 페이지 테이블로 프레임을 찾은 뒤 같은 오프셋을 더한다. 매 접근마다 데이터를 옮기는 것이 아니라 주소를 변환하는 과정이다. 0부터 세므로 오프셋 4는 구간의 다섯 번째 바이트다.

**설명 후 사용자 답변:** 오프셋 4는 가상 주소 20에서 가상 페이지 1의 시작점을 뺀 값이라고 설명했다. 물리 주소는 물리 프레임 번호에 16을 곱한 값에 오프셋을 더한다고 연결했다.

**최종 피드백:** 오프셋의 의미와 물리 주소 계산식을 정확히 연결했다. 페이지 번호와 시작 주소도 가상 주소와 페이지 크기로 계산할 수 있으며, 페이지 번호는 나눗셈의 몫, 오프셋은 나머지라고 보완했다. 물리 프레임 번호는 가상 주소에서 직접 계산하는 것이 아니라 페이지 테이블의 대응으로 얻는다.

**확인 범위:** 같은 예제의 설명 후 오프셋 산출과 물리 주소 계산 원리를 답했다. 새로운 숫자 사례의 독립적인 계산이나 페이지 테이블 구조·페이지 폴트까지 확인한 것은 아니다.
