# 인덱스와 조회 성능

- 날짜: 2026-11-12 (Asia/Seoul)

- 목표: 인덱스의 탐색 원리, 유지 비용, 복합 인덱스의 순서와 성능 판단을 설명하기.
- 이전 학습: [SQL JOIN과 집계](2026-11-10-sql-joins-aggregation.md)

## 핵심 개념

- 인덱스는 검색을 돕는 자료구조이며 테이블에 추가하는 새 데이터 열이 아니다. 이번에는 정렬된 키와 탐색 경로를 이용하는 트리형 인덱스를 중심으로 설명했다.
- 조건에 맞는 소수의 행을 찾을 때 인덱스는 검사할 데이터의 양을 줄일 수 있다. 인덱스가 항상 더 빠르다는 뜻은 아니다.
- 데이터 추가·삭제 또는 인덱스가 있는 값의 변경에는 관련 인덱스를 유지하는 비용이 들고, 인덱스는 저장 공간도 차지한다.
- 오름차순 (member_id, created_at) 복합 인덱스는 회원 ID가 우선이고 같은 회원 안에서 날짜가 정렬된다. 두 개의 독립적인 인덱스가 아니다.
- 이미 존재하는 인덱스의 생성 비용은 해당 SELECT마다 발생하는 비용이 아니다. 조회 시에는 인덱스 탐색·읽기와 필요한 원본 행 접근 등을 비교한다.

## 확인 문제와 피드백

### 1. COUNT·NULL·DISTINCT 복습

**질문:** 회원을 기준으로 신고와 로그인 이력을 회원 ID만으로 LEFT JOIN한 결과가 (A,101,201), (A,101,202), (B,NULL,203), (B,NULL,204)다. 각 열은 회원·신고 ID r.id·로그인 ID l.id다. 추가 필터 없이 회원별로 묶을 때 COUNT(*)·COUNT(r.id)·COUNT(DISTINCT r.id)의 값과 A의 반복 이유, B의 COUNT(r.id) 값의 이유는?

**사용자 답변:** A는 2·2·1, B는 2·0·0. “count는 null을 못세”.

**피드백:** 여섯 값 모두 정확하다. 다만 NULL을 제외하는 것은 COUNT(열)과 COUNT(DISTINCT 열)이며 COUNT(*)는 NULL이 들어 있는 행도 센다. A의 신고 한 건이 두 로그인 이력과 연결되어 반복된다는 이유는 사용자가 직접 설명하지 않아 보완했다. 이전 NULL 사례의 계산은 개선됐지만 일반화한 표현과 행 조합 원리는 계속 복습한다.

### 2. 이메일 인덱스는 무엇을 줄일까?

**질문:** 이메일이 서로 다른 회원 100만 명에서 아래 쿼리를 실행한다. 다른 사용 가능한 이메일 검색 인덱스는 없다. email 인덱스를 새로 만들면 이 조건에 사용할 수 있고 DB가 사용한다고 가정한다. 인덱스 유무에 따른 탐색 방식과 빨라질 수 있는 이유는?

```sql
SELECT id, name
FROM members
WHERE email = 'member@example.com';
```

**사용자 답변 요지:** 인덱스가 있으면 조회 범위를 나눠서 찾고, 없으면 값을 하나씩 비교해야 해서 더 오래 걸린다.

**피드백:** 검색 범위를 좁혀 비교할 데이터의 양을 줄인다는 원리를 정확히 설명했다. 테이블 전체를 읽으며 조건을 확인하는 방식을 풀 테이블 스캔이라고 설명했다. 많은 행 중 소수를 찾는 이번 조건의 장점으로 한정했다.

### 3. 모든 열에 인덱스를 만들면 좋을까?

**질문:** 조회를 빠르게 하려고 모든 회원 열에 인덱스를 만들자는 제안을 평가해 보자. 회원 추가·이메일 변경 시의 추가 작업과 저장 공간을 중심으로 설명하기.

**사용자 답변 요지:** 항상 좋지는 않다. 이메일 변경 시 인덱스 값도 변경해야 하고 “인덱스라는 데이터 열”의 공간도 추가로 필요하다. 잘 설정하면 최적화에 도움이 될 것 같다.

**피드백:** 유지 비용·저장 비용과 무조건 많은 인덱스가 좋지 않다는 판단은 정확하다. 인덱스는 새 열이 아닌 검색 자료구조라고 용어를 보완했다. 새 회원 추가 시 관련 인덱스에도 항목이 추가되는 과정은 보충 설명이다. 모든 UPDATE가 모든 인덱스 키를 변경한다고 일반화하지 않는다.

**사용자 중간 질문:** 보통 많이 비교하는 데이터를 기준으로 인덱스를 만드는가?

**보충 설명:** WHERE·JOIN 조건이나 ORDER BY 정렬에 사용하는 열을 후보로 본다. 실제 쿼리의 빈도, 조건으로 줄어드는 행 수, 함께 쓰는 조건과 순서, 쓰기 빈도·저장 공간을 함께 고려한다. 실행 계획과 측정으로 확인한다. 이 선택 기준의 적용 능력은 설명만으로 검증됐다고 보지 않는다.

### 4. 복합 인덱스의 열 순서

**질문:** 오름차순 (member_id, created_at) 인덱스에서 ① member_id=10 AND created_at>='2026-11-05'와 ② created_at>='2026-11-05' 중 어느 조건이 정렬 순서에 따라 한 구간으로 범위를 좁히기 쉬운가? 이유도 설명하기.

**사용자 답변 요지:** 첫 번째. 회원 ID를 찾고 생성일을 맞추면 날짜를 바로 탐색하는 것보다 절약될 것 같다. 하지만 원리가 직관적으로 이해되지 않는다고 설명을 요청했다.

**피드백과 보충:** 선택과 선행 열의 범위를 이용한다는 방향은 맞다. 회원 번호순 서류철 안의 날짜순 기록에 비유해 다음 순서를 펼쳤다.

| 회원 | 날짜 | ① 포함 여부 | ② 포함 여부 |
|---|---|---|---|
| 10 | 11-01 | 제외 | 제외 |
| 10 | 11-06 | 포함 | 포함 |
| 10 | 11-10 | 포함 | 포함 |
| 20 | 11-02 | 제외 | 제외 |
| 20 | 11-07 | 제외 | 포함 |
| 20 | 11-11 | 제외 | 포함 |

날짜는 모두 2026년이다. ①은 10번 회원 안의 연속 구간이고, ②는 회원별 구간에 흩어진다. 날짜는 각 회원 안에서 정렬되며 전체 날짜순은 아니다. 트리의 탐색 경로로 시작 범위를 찾는 원리이며 모든 회원을 순차 검색하거나 SQL을 두 번 실행한다는 뜻이 아니다. 후행 열만 조건에 있어도 인덱스 스캔 등 활용 여지는 있으므로 인덱스를 절대 못 쓴다고 일반화하지 않는다.

**보충 후 사용자 반응:** “알겠어 이제 다음문제 진행해줘”. 진행 의사를 확인했으며 새 사례에서 원리를 설명한 것으로 기록하지 않는다.

### 5. 95%를 조회할 때 전체 스캔을 선택한다면?

**질문:** 회원 100만 명 중 95만 명이 ACTIVE다. status 인덱스는 있지만 name·email은 그 인덱스에 없다. SELECT id,name,email FROM members WHERE status='ACTIVE';의 실행 계획이 테이블 전체 스캔을 선택했다. 무조건 잘못된 계획인가? 읽는 양과 실제 성능 확인 방법으로 설명하기. 실제 서비스에서 측정한 사례가 아닌 가상 문제다.

**사용자 답변:** 인덱스를 만드는 시간과 그것을 통해 읽는 작업 시간보다, 100만 명 중 95%를 full table scan으로 읽는 것이 유리할 것 같다.

**피드백:** 전체 스캔이 유리할 수 있다는 결론은 맞다. 그러나 이미 존재하는 인덱스를 조회할 때 다시 만드는 것은 아니다. 비교할 것은 생성 비용이 아니라 인덱스를 읽고 필요한 행 데이터를 가져오는 비용이다. 전체 스캔은 95만 행만 읽는 것이 아니라 전체 100만 행을 살피고 조건에 맞는 95만 행을 반환한다.

**보충 설명:** 이번처럼 인덱스에 조회 열이 모두 없으면 대상 행에 추가 접근이 필요하다. MySQL InnoDB의 보조 인덱스는 기본 키로 행 데이터에 접근한다. 대부분 행이 필요하면 인덱스 경유 비용을 더하는 것보다 전체를 읽는 방식이 유리할 수 있다. 95%라는 수치만으로 항상 빠르다고 단정하지 않는다.

**측정 관련 확인 범위:** 사용자는 확인 방법에는 답하지 않았다. 같은 데이터·환경·부하와 유사한 캐시 조건에서 두 접근 방식의 실제 시간을 반복 비교하고, 실행 계획에서 접근 방식과 처리 행 수를 확인하도록 설명했다. EXPLAIN은 계획, EXPLAIN ANALYZE는 실제 실행 시간·행 수 등을 확인하는 도구다. 사용자가 실제 측정하거나 계획 해석을 수행한 것으로 기록하지 않는다.
