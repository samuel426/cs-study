## 핵심 개념

CPU 스케줄링은 실행 가능한 스레드 중 누구에게 CPU를 배정할지 결정하는 일이고, 스케줄러는 그 선택을 담당한다. 컨텍스트 스위칭은 실제로 실행 대상을 바꾸며 상태를 저장·복원하는 과정이다.

오늘은 운영체제가 스케줄링하는 스레드를 기준으로, 한 코어에서 한 번에 스레드 하나만 실행한다고 가정했다. Java의 스레드 상태 열거형과는 구분한다.

| 상태 | 의미 | 대표적인 전이 |
|---|---|---|
| 준비 | CPU만 배정받으면 실행할 수 있음 | CPU 배정 시 실행으로 |
| 실행 | 현재 CPU에서 명령을 실행함 | 선점되면 준비로, 입출력을 기다리며 멈추면 대기로 |
| 대기 | 입출력 완료 같은 사건을 기다리며 실행을 멈춤 | 기다리던 조건이 충족되면 준비로 |

**선점**은 계속 실행할 수 있는 스레드를 운영체제가 중단시키고 다른 스레드에 CPU를 배정하는 것이다. 한 차례 실행에 배정하는 시간을 **타임 슬라이스**라고 한다. 정책에 따라 이 시간이 끝나기 전에도 높은 우선순위의 스레드가 준비되어 선점할 수 있다. 큐는 순서를 관리하는 자료구조이며, 큐 사용 자체가 실행 시간 제한을 뜻하지 않는다.

## 확인 문제와 피드백

### 1. 네트워크 응답을 기다리는 A와 CPU를 기다리는 B의 상태는?

**질문:** A는 네트워크 응답이 올 때까지 실행을 멈췄고, B는 계산할 준비를 마쳤지만 CPU를 배정받지 못했다. 각각 어떤 상태이며, CPU가 비었을 때 둘 중 누구를 실행 대상으로 고를 수 있을까? 이유도 설명해 줘.

**내 답변 요지:** A는 대기, B는 준비. CPU가 비면 이미 준비된 B가 보통 실행 대상으로 선택될 것 같다.

**피드백:** 상태 구분과 B 선택은 맞다. 응답이 아직 오지 않았다면 A는 실행 조건이 충족되지 않아 선택 대상이 아니다. 둘 중 B만 CPU를 배정받아 실행할 수 있다.

### 2. B 실행 중 A의 네트워크 응답이 도착하면 반드시 즉시 전환하는가?

**질문:** B가 계산을 실행하던 중 A가 기다리던 네트워크 응답이 도착했다. B를 즉시 멈추고 반드시 A를 실행해야 할까? A의 상태 변화와 함께 이유를 설명해 줘.

**내 답변 요지:** 큐처럼 스레드마다 코어 점유 시간이 정해져 있으면 B가 진행하다 비키고, 그렇지 않으면 A가 B의 작업이 끝날 때까지 기다릴 것 같다.

**피드백:** 정책에 따라 실행 기회가 달라진다는 방향은 맞다. A는 대기에서 준비로 바뀌지만 즉시 실행이 보장되지는 않는다. 상태 변화는 답변에서 직접 설명하지 않아 피드백으로 보완했다.

- 타임 슬라이스를 다 쓰기 전에도 정책에 따라 선점할 수 있다.
- 비선점 방식에서도 B가 입출력 대기에 들어가거나 자발적으로 CPU를 양보하면 작업 종료 전에 A에게 기회가 올 수 있다.
- 선점된 B가 계속 실행 가능한 경우에는 실행에서 준비로 바뀐다. 입출력 대기 상태와 다르다.

### 3. 긴 계산 도중 클릭 처리에 선점이 도움이 되는 이유와 잦은 전환의 단점은?

**질문:** B는 10초 동안 입출력 대기나 자발적 양보 없이 계산하고, 도중에 클릭을 처리할 A가 준비 상태가 됐다. 선점이 왜 도움이 될까? 전환 간격을 무조건 짧게 만들면 어떤 단점이 생길까?

**내 답변 요지:** 중단·전환·A 시작까지 비용이 들어서 차라리 선점이 이득일 수 있다고 생각했다. 전환 간격이 너무 짧으면 스위칭 비용 때문에 전체 실행 시간이 길어질 수 있다.

**피드백:** 잦은 전환의 비용과 전체 실행 시간 증가 가능성은 정확하다. 첫 문장은 이득과 비용의 관계가 불명확해 보완했다. 선점도 전환 비용이 들지만, A가 B의 남은 계산이 끝나기를 기다리지 않고 클릭에 반응할 기회를 얻는 것이 이점이다. 예를 들어 B의 계산이 8초 남았다면, 그 시간을 다 기다리지 않고 A를 실행할 수 있다.

응답 시간을 줄이는 것과 전체 계산을 빨리 끝내는 것은 서로 다른 목표다. 선점의 이점에 대한 이 설명은 피드백으로 제공했으며, 사용자 답변으로 확인된 이해와 구분한다.

### 4. 채팅 앱과 사진 1만 장 변환에서 더 중요한 성능 기준은?

**질문:** 버튼을 누르면 반응해야 하는 채팅 앱과 사용자가 자는 동안 사진 1만 장을 변환하는 작업에서, 각각 응답 시간과 처리량 중 어느 기준을 더 중요하게 보겠어? 이유도 설명해 줘.

**내 답변 요지:** 채팅 앱은 반응이 빨라야 의미가 있어 응답 시간이 중요하다. 사진 변환은 처리량이 중요하며, 처리량이 빨라야 응답 시간을 줄일 수 있기 때문이라고 설명했다.

**피드백:** 기준 선택 두 개와 채팅 앱의 이유는 맞다. 사진 변환의 이유는 응답 시간과 전체 작업 완료 시간을 구분해야 한다.

| 기준 | 의미 |
|---|---|
| 응답 시간 | 요청 후 첫 반응까지 걸리는 시간. 짧을수록 좋음 |
| 처리량 | 단위 시간에 완료하는 작업의 양. 높을수록 좋음 |
| 전체 작업 완료 시간 | 주어진 작업 전체를 마칠 때까지 걸리는 시간 |

일정한 처리 속도를 가정하면 1만 장을 초당 100장 처리할 때 100초, 초당 200장 처리할 때 50초가 걸린다. 같은 양의 작업에서 처리량이 높으면 전체 완료 시간이 줄어들지만, 첫 반응도 반드시 빨라진다는 뜻은 아니다.

### 5. 계속 선택에서 밀리는 C의 상태와 실행 기회를 주는 방법은?

**질문:** 스케줄러가 항상 우선순위가 높은 스레드만 고르는데 그런 작업이 계속 들어와, 낮은 우선순위의 C가 CPU를 받지 못한다. C는 CPU만 받으면 계산할 수 있다. C는 준비와 대기 중 어떤 상태이며, C도 실행 기회를 얻도록 스케줄러가 무엇을 고려하면 좋을까? 알고리즘 이름 대신 아이디어로 설명해도 된다.

**내 답변:** “준비, 실행 시간도 스케줄러가 고려하면 좋겠네 SJF 이건가?”

**피드백:** 준비 상태라는 답은 맞다. 실행 시간이 무엇을 뜻하는지는 답변만으로 확정할 수 없다. 앞으로 필요한 CPU 실행 시간이 짧은 작업을 먼저 고른다는 뜻이라면 **SJF(Shortest Job First, 짧은 작업 우선)**와 연결된다. 엄밀히는 다음 **CPU 버스트**, 즉 입출력 대기 등으로 멈추기 전까지 이어지는 CPU 실행 구간의 길이를 기준으로 한다.

하지만 짧은 작업이 계속 들어오면 긴 작업은 SJF에서도 계속 밀릴 수 있다. 실행 가능한데도 CPU를 계속 배정받지 못하는 현상을 **기아(starvation)**라고 한다.

이번 문제에서는 준비 상태로 **얼마나 오래 실행 기회를 기다렸는지**를 고려하는 방법이 도움이 된다. 오래 기다린 작업의 우선순위를 점차 높이는 **에이징(aging)**이 한 예다. 여기서 기다린 시간은 입출력 대기 상태에 머문 시간이 아니라 CPU 배정을 기다린 시간이다. SJF와 에이징의 구분은 보충 설명이며 별도 확인 문제를 풀지는 않았다. [참고: Johns Hopkins University 강의 자료](https://www.cs.jhu.edu/~yairamir/cs418/os2/tsld031.htm)

## 오늘 보완한 생각

아래는 피드백으로 보완한 내용이며, 설명 후 별도 답변으로 모두 재검증한 것은 아니다.

- 입출력이 끝나면 실행 가능해지지만, 반드시 즉시 CPU를 받는 것은 아니다.
- 비선점이어도 현재 스레드가 입출력 대기나 자발적 양보로 CPU를 놓을 수 있다.
- 선점은 전환 비용을 감수하며 응답성을 개선할 수 있다. 전체 완료 시간을 항상 줄이지는 않는다.
- 높은 처리량과 짧은 응답 시간은 같은 뜻이 아니다.
- 짧은 작업 우선 선택과 오래 기다린 작업의 기아 방지는 다른 고려 사항이다.

답변으로 확인한 내용은 준비·대기 구분, 잦은 전환의 비용, 두 작업의 성능 기준 선택과 채팅 앱에서 응답 시간이 중요한 이유다. 응답 시간과 완료 시간의 구분, 선점의 이점, SJF와 에이징은 다음 수업에서 복습한다.
